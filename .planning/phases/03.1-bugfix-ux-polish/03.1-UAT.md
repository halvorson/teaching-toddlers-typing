## Tests

### 1. MENU-04 — drifting parallax background visibly rendering
expected: The two drifting layers are visibly animating on the home menu and disappear during gameplay.
result: **ISSUE → FIX ROUND 1 → STILL ISSUE → FIX ROUND 2 → awaiting re-confirmation.**
  Round 1: user reported background not visible on live site. Live diagnosis via claude-in-chrome
  found the real root cause was NOT the color-mix() hypothesis this phase's plan targeted — it was
  `index.html`'s inline `html, body { background: #0A0E1B; }` rule causing canvas-background
  propagation to mask `position: fixed` + negative-`z-index` layers. Fixed in commit `dfbe03d`
  (scoped background to `body` only), deployed, verified visible via claude-in-chrome on the live
  redeployed site.
  Round 2: user re-checked and still could not see it on their large screen. Root-cause fix was
  correct (masking bug resolved) but the *effect* was too subtle to perceive — original alpha
  values were only 10%/6%. Boosted to 24%/16% (commit `765ae2e`), verified visually via local
  `npm run preview` before deploy — clearly visible. **Awaiting user re-confirmation.**

### 2. TRAIL-03 — star trail visibly rendering during gameplay
expected: |
  Play any mode and get 2-3 correct matches. Glowing accent-tinted stars visibly
  accumulate on screen. Return to the menu and confirm the trail is hidden. If stars
  are still invisible, run `document.querySelectorAll('.star-trail__star').length` in
  DevTools to disambiguate a CSS-only visibility cause from a DOM-append bug.
result: **ISSUE → FIX ROUND 1 → user confirmed working but too subtle → FIX ROUND 2 (intensity
  boost) → awaiting re-confirmation.** Same canvas-masking root cause and fix as MENU-04 round 1.
  `document.querySelectorAll('.star-trail__star').length` confirmed stars were correctly appended
  to the DOM even while invisible (ruled out a DOM-append bug). After round 1 fix + redeploy, user
  confirmed the trail was working but wanted it "punched up" on a large screen. Boosted star glow
  (core alpha 70%→90%, box-shadow blur 6px→12px/45%→75%, dot size 6px→8px; commit `765ae2e`).
  Verified visually via local `npm run preview` (zoomed screenshot of an accumulated star showed a
  clearly visible glow). **Awaiting user re-confirmation.**

### 4. AUDIO-03 — correct TTS pronunciation, no "Capital" prefix
expected: |
  With sound enabled, press a matching physical key in Letters or Alphabet mode and
  listen to the spoken letter for several different letters. The browser speaks just
  the bare letter name (e.g. "E" spoken as "Ee"), never "Capital E" or any other
  prefix. Numbers mode's digit pronunciation is unchanged.
result: **PASS (general "Capital" prefix bug) → NEW ISSUE FOUND (2 specific letters) → FIX SHIPPED
  → awaiting re-confirmation.** User confirmed the original "Capital E"-style prefix bug is fixed
  and most letters sound right, but reported A sounds like "I" and G sounds like "C" on their
  Mac + Chrome/Safari setup. Traced via claude-in-chrome: the code correctly requests
  LETTER_WORDS['A']/['G'] ("Ay"/"Jee") every time — not a logic bug, a respelling-accuracy issue
  on the active voice. Fixed (commit `68d9139`): G "Jee"→"Gee" (a real, common English word,
  should be far more reliably pronounced than the invented "Jee"); A "Ay"→"Ey" (leans on the
  more reliable "-ey" digraph pattern — they/grey/obey — vs. "ay"'s genuine ambiguity with the
  interjection reading). **Cannot verify audio output directly (no audio-capture tool) — this is
  a best-effort respelling fix, not an audio-confirmed one. Needs a human listening pass
  specifically on A and G again.**
