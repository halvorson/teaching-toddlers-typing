## Warnings

### WR-04: `sharePending` re-entrancy flag isn't scoped to a mount, so a Share click can silently no-op after a quick screen change

**File:** `src/menu.ts:58, 65, 198-216, 223-225, 398-399`

**Issue:**
`sharePending` is declared once at module scope (`src/menu.ts:65`) and is the sole guard preventing two overlapping `runShare()` calls (fixing WR-02 correctly for the single-mount case). But unlike `mountGeneration`, which both `mountMenu()` (`src/menu.ts:224`) and `unmountMenu()` (`src/menu.ts:399`) increment on every mount/unmount boundary, `sharePending` is never reset by either function — it is only cleared in `runShare()`'s own `finally` block (`src/menu.ts:213-215`), which runs whenever that specific call's `await shareCurrentUrl()` eventually settles:

```ts
async function runShare(): Promise<void> {
  if (sharePending) return // a previous call is still in flight — ignore
  sharePending = true
  try {
    const myGeneration = mountGeneration
    const result = await shareCurrentUrl()
    if (myGeneration !== mountGeneration) return // <- stale mount handled here
    ...
  } finally {
    sharePending = false // <- but the flag itself isn't mount-scoped
  }
}
```

Concrete repro: on the menu, click Share. `shareCurrentUrl()` starts (`clipboard.ts`'s `navigator.clipboard.writeText` — some browsers/permission-policy combinations show a modal permission prompt here that can remain open for an arbitrary length of time before the promise settles). While that promise is still pending, activate a different row — e.g. Settings, then Back — which round-trips through `unmountMenu()` → `mountSettingsScreen()` → `unmountSettingsScreen()` → `mountMenu()`. `mountGeneration` is bumped twice by this round trip (correctly invalidating the original call's eventual DOM writes via the `myGeneration !== mountGeneration` check), but `sharePending` is untouched and is still `true` from the original, still-pending call. Back on the freshly remounted menu, clicking Share now hits `if (sharePending) return` and does *nothing at all* — no "Copied!" feedback, no fallback panel, no visible error — until the original stale promise finally resolves or rejects and its `finally` block fires. On a fast Clipboard API resolution this window is milliseconds and invisible; on a browser that shows a blocking permission prompt, or simply if a parent double-taps a slow touchscreen, the Share row can appear completely unresponsive for a noticeably longer window with zero feedback to the user, which is exactly the class of "silent no-op" bug WR-02 was fixing for the within-mount case.

**Fix:** Scope the guard to the mount, the same way `mountGeneration` already is — either reset `sharePending` alongside the other module state in `mountMenu()`/`unmountMenu()`, or fold it into the existing generation counter instead of using a separate boolean:

```ts
export function mountMenu(container: HTMLElement, handlers: MenuHandlers): void {
  mountGeneration++
  sharePending = false // a stale in-flight call from the previous mount no
                        // longer blocks Share on this mount
  ...
}

export function unmountMenu(): void {
  mountGeneration++
  sharePending = false
  ...
}
```
Note this alone doesn't stop the *original* stale call from still doing its (now-discarded, thanks to the `myGeneration` check) work — it just stops that stale call's flag from blocking the *new* mount's legitimate clicks, which is the actual user-facing symptom.

### IN-01: `.menu-label` class applied in JS has no corresponding CSS rule

**File:** `src/menu.ts:289-290`, `src/style.css` (no matching selector exists)

**Issue:** The Share row's label `<span>` is given `className = 'menu-label'` (`src/menu.ts:290`), but `style.css` has no `.menu-label` rule anywhere (confirmed via search — the only match for `menu-label` in the codebase is the assignment site itself). It renders correctly only because it inherits `color`/`font-family`/`font-weight` from the parent `.menu-item` button. Not a functional defect, but a styling hook that doesn't exist reads as either dead code or a forgotten rule. Unchanged from the prior review; not in scope for the iteration-1 fix pass.

**Fix:** Either add an (even empty/documented) `.menu-label { }` rule in `style.css` for clarity, or drop the class from the span if it's not intended to be a styling hook.

### IN-03: `handleClick`'s branch chain silently no-ops for the `stats` row with no exhaustiveness check

**File:** `src/menu.ts:307-325`

**Issue:** `handleClick` branches with `if (isGameplayRow(row)) ... else if (row === 'quit') ... else if (row === 'share') ... else if (row === 'settings') ...` and falls through to nothing for `row === 'stats'`, relying on a trailing comment ("stats stays undispatched") rather than a compiler-enforced exhaustiveness check. Intentional per the comment (Phase 4 owns that screen) and not a bug today, but `MenuRow` isn't switched over exhaustively, so a future new row value added to `MENU_ROWS` without a corresponding branch would silently no-op with no type-level warning. Unchanged from the prior review.

**Fix:** Optional — convert to a `switch (row)` with a `default` branch asserting `row` is `never` (or an explicit `stats` case with a comment) to get a compile-time reminder whenever `MenuRow` gains a new member.
