# Phase 03.1: Code Review Report

**Reviewed:** 2026-08-14T19:52:56Z
**Depth:** standard
**Files Reviewed:** 4

## Summary

Reviewed `src/menu.ts`, `src/style.css`, `src/audio.ts`, and `.claude/CLAUDE.md`. `audio.ts` is solid — every browser API call is wrapped defensively, both entry points are independent as documented, and the pronunciation tables match `game.ts`'s pools. `.claude/CLAUDE.md` is documentation only; no functional defects apply.

`menu.ts` is the highest-risk file in this set. It implements a delegated event-listener pattern across four handlers (click, hover, focusin, keydown), and three of the four correctly scope themselves to `button[data-row]` elements before acting — but `handleKeydown` does not, so it also intercepts keyboard input from the Share row's manual-copy fallback `<input>`, which lives inside the same `<nav>` and therefore receives bubbled keydown events. This actively breaks the "last resort" copy-fallback tier that the file's own header comment says exists precisely for when the automatic clipboard tiers fail. A second, currently-masked defect: `unmountMenu()` cleans up the wrong DOM node, leaving an orphaned empty `<div class="home-menu">` behind every time the menu is torn down — invisible today only because every caller in this codebase happens to immediately follow `unmountMenu()` with another mount function that does its own `container.replaceChildren()`. A third issue is a real (if narrow) race: nothing prevents two overlapping `runShare()` invocations within the same mount, which can produce duplicate DOM fallback panels or a premature "Copied!" reversion.

## Critical Issues

### CR-01: Menu's roving-focus keydown handler is not scoped to menu buttons, hijacking keyboard input inside the Share manual-copy fallback box

**File:** `src/menu.ts:312-337` (compare with the scoping done at `src/menu.ts:292-295`, `339-344`, and `352-355`)

**Issue:**
`handleClick`, `handleHover`, and `handleFocusIn` all guard themselves with `target.closest<HTMLButtonElement>('button[data-row]')` and bail out if the event didn't originate from (or bubble through) one of the seven menu buttons. `handleKeydown` has no such guard:

```ts
const handleKeydown = (event: KeyboardEvent): void => {
  if (event.repeat) return
  switch (event.key) {
    case 'ArrowDown':
      event.preventDefault()
      focusRow(focusIndex + 1)
      break
    case 'ArrowUp': ...
    case 'Home': ...
    case 'End': ...
  }
}
```

It's registered with `nav.addEventListener('keydown', handleKeydown)` (`src/menu.ts:366`). When the Share row's clipboard tiers fail, `renderManualFallback()` inserts a read-only `<input class="share-manual__url">` as a sibling of the Share button *inside* `groupUtility`, which is itself inside `nav` (`src/menu.ts:134-181`, insertion at `shareButtonEl.after(panel)`, line 153). That input is therefore a descendant of `nav`, so any keydown fired while it has focus bubbles up and reaches `handleKeydown` — which was written assuming only the seven roving `button[data-row]` elements could ever be focus targets inside `nav`.

Concretely: a parent whose browser denies clipboard access (a routine occurrence — non-HTTPS context, an iframe, or a simple permission denial) sees the manual-copy box, which the code auto-selects via `urlBox.select()` so a single Cmd/Ctrl-C works. If that parent instead presses `Home` or `End` to review the (potentially long) URL, or presses an arrow key out of habit, `handleKeydown` calls `event.preventDefault()` and then `focusRow(...)`, which calls `.focus()` on a menu button — silently yanking keyboard focus away from the copy box they were just given as their only remaining way to grab the link, with no visible explanation of why focus moved.

This is exactly the interaction the fallback tier exists to guarantee works when everything else has failed, and it is the one delegated handler in the file that skipped the scoping discipline every other handler follows.

**Fix:** Add the same scoping guard used by the other three handlers, e.g.:
```ts
const handleKeydown = (event: KeyboardEvent): void => {
  if (event.repeat) return
  const target = event.target as HTMLElement
  if (!target.closest<HTMLButtonElement>('button[data-row]')) return
  switch (event.key) {
    ...
  }
}
```

## Warnings

### WR-01: `unmountMenu()` doesn't remove the menu's outer wrapper — leaves an orphaned empty `<div class="home-menu">` behind

**File:** `src/menu.ts:213-214`, `289-290`, `376-390`

**Issue:** `mountMenu()` builds an outer `wrapper` div, appends the title and `nav` into it, then appends `wrapper` (not `nav`) to `container`:
```ts
const wrapper = document.createElement('div')
wrapper.className = 'home-menu'
...
wrapper.appendChild(nav)
container.appendChild(wrapper)
```
but the module tracks `mountedNav = nav` — the *inner* element — not `wrapper`. `unmountMenu()`'s cleanup then does:
```ts
if (mountedNav?.parentElement) {
  mountedNav.parentElement.replaceChildren()
}
```
`mountedNav.parentElement` is `wrapper`, so this only empties `wrapper`'s children (the title and `nav`) — it does not detach `wrapper` itself from `container`. After `unmountMenu()` runs, an empty `<div class="home-menu"></div>` remains attached to `#app`.

Compare with `game-screen.ts` (`mountedContainer = container`, so `mountedContainer.replaceChildren()` correctly empties the real container) and `settings.ts` (the panel is appended directly to `container`, so `mountedPanel.parentElement` *is* `container`). `menu.ts` is the only one of the three screen modules with an extra wrapper layer, and its unmount function wasn't updated to account for it.

This currently has no visible effect only because every call site in `main.ts`'s `mountScreen()` invokes `unmountMenu()` immediately followed, in the same synchronous call, by another mount function that itself calls `container.replaceChildren()` — which incidentally removes the orphaned wrapper too. The moment any future code path calls `unmountMenu()` without an immediate full-container remount (e.g., a "just hide the menu" flow, or a different composition), the empty div leaks permanently. It also means the doc comment on `unmountMenu()` — "resets all module-level menu state" — overstates what the function actually guarantees about the DOM.

**Fix:** Track the actual mounted root, not the inner `nav`:
```ts
let mountedWrapper: HTMLElement | null = null
// ...in mountMenu():
mountedWrapper = wrapper
// ...in unmountMenu():
if (mountedWrapper?.parentElement) {
  mountedWrapper.parentElement.replaceChildren()
}
mountedWrapper = null
```

### WR-02: Concurrent `runShare()` invocations aren't guarded within a single mount, allowing duplicate fallback panels / stale timers

**File:** `src/menu.ts:190-202`, `292-310`, `115-124`, `134-181`

**Issue:** `mountGeneration` only protects against a `runShare()` call outliving a *mount/unmount* boundary (`src/menu.ts:191-196`). It does nothing to prevent two overlapping `runShare()` calls *within* the same mount — e.g., a double-click (or double-tap) on the Share row before the first `shareCurrentUrl()` promise resolves. `handleClick`'s share branch (`src/menu.ts:302-304`) calls `resetShareFeedback()` then fires `void runShare()` with no re-entrancy guard, so a second click starts a second, fully independent `runShare()` while the first is still pending.

Two concrete consequences if both calls resolve to `'manual-required'` (clipboard denied): `renderManualFallback()` (`src/menu.ts:134-181`) is invoked twice, and each call does `shareButtonEl.after(panel)` — each insertion lands immediately after the Share button, so the second call's panel is inserted *before* the first call's panel rather than replacing it. The module-level `shareFallbackEl` only ever tracks the most recent panel, so the earlier one becomes an orphaned, untracked DOM node that `resetShareFeedback()`/`unmountMenu()` can no longer find and remove — it survives until the next full menu remount.

If both calls instead resolve to `'copied'`/`'fallback-executed'`, `showCopiedFeedback()` (`src/menu.ts:115-124`) runs twice and each call overwrites `copiedTimeoutId` without clearing the previous timer, so the earlier timer is never cancelled. If it fires between the two calls' scheduled reverts, the "Copied!" label can flicker back to "Share" earlier than the more recent click's own 1500ms window would suggest.

**Fix:** Guard against re-entrancy, e.g. track a `sharePending` boolean (or bump a dedicated share-generation counter on every click, not just mount/unmount) and early-return from the share branch of `handleClick` while a previous `runShare()` is still in flight:
```ts
let sharePending = false
async function runShare(): Promise<void> {
  if (sharePending) return
  sharePending = true
  try {
    const myGeneration = mountGeneration
    const result = await shareCurrentUrl()
    if (myGeneration !== mountGeneration) return
    if (result !== 'manual-required') { showCopiedFeedback(); return }
    renderManualFallback()
  } finally {
    sharePending = false
  }
}
```

### WR-03: `voiceschanged` listener is registered `{ once: true }`, but some browsers populate voices progressively

**File:** `src/audio.ts:105-119`

**Issue:** `primeVoices()`'s own doc comment acknowledges that voice-loading behavior differs across browsers ("Chrome loads voices asynchronously... Firefox and Safari load them synchronously and may never fire `voiceschanged` at all"), but the listener that reconciles the asynchronous case is registered with `{ once: true }`:
```ts
window.speechSynthesis.addEventListener('voiceschanged', () => {
  cachedVoices = window.speechSynthesis.getVoices()
}, { once: true })
```
If a browser fires `voiceschanged` more than once as its voice list populates incrementally (observed in some Chromium versions/OS combinations), only the first snapshot is ever cached; later, more-complete voice lists are silently ignored for the rest of the session. The failure mode is graceful (worst case, `speakTarget()` falls back to the browser's default voice instead of a language-matched one — `src/audio.ts:204-209`), so this is not correctness-breaking, but it's a real gap in a function whose whole purpose is reconciling exactly this kind of inconsistency.

**Fix:** Drop `{ once: true }` and instead resync on every `voiceschanged` firing (idempotent — reassigning `cachedVoices` from `getVoices()` again is cheap and always safe):
```ts
window.speechSynthesis.addEventListener('voiceschanged', () => {
  cachedVoices = window.speechSynthesis.getVoices()
})
```

### IN-01: `.menu-label` class applied in JS has no corresponding CSS rule

**File:** `src/menu.ts:275-276`, `src/style.css` (no matching selector exists)

**Issue:** The Share row's label `<span>` is given `className = 'menu-label'` (`src/menu.ts:276`), but `style.css` has no `.menu-label` rule anywhere. It currently renders correctly only because it inherits `color`/`font-family`/`font-weight` from the parent `.menu-item` button — there's no functional defect, but the class is a styling hook that doesn't exist, which reads as either dead code or a forgotten rule.

**Fix:** Either add an (even empty/documented) `.menu-label { }` rule in `style.css` for clarity, or drop the class from the span if it's not intended to be a styling hook.

### IN-03: `handleClick`'s branch chain silently no-ops for the `stats` row with no exhaustiveness check

**File:** `src/menu.ts:296-310`

**Issue:** `handleClick` branches with `if (isGameplayRow(row)) ... else if (row === 'quit') ... else if (row === 'share') ... else if (row === 'settings') ...` and falls through to nothing for `row === 'stats'`, relying on a trailing comment ("stats stays undispatched") rather than a compiler-enforced exhaustiveness check. This is intentional per the comment (Phase 4 owns that screen) and not a bug today, but the `MenuRow` union isn't switched over exhaustively, so a future new row value added to `MENU_ROWS` without a corresponding branch would silently no-op with no type-level warning.

**Fix:** Optional — convert to a `switch (row)` with a `default` branch asserting `row` is `never` (or an explicit `stats` case with a comment) to get a compile-time reminder whenever `MenuRow` gains a new member.
