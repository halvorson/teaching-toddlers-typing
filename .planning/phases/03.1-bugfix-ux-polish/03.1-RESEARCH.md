## Summary

This phase is four regression bugfixes plus one net-new layout requirement, on a codebase with **zero build-pipeline abnormalities**. The single most load-bearing finding of this research: **the live GitHub Pages deployment is byte-for-byte identical to what `npm run build` produces from the current `main` branch HEAD right now** — verified directly by building locally and diffing both the CSS and JS bundles against `curl`-fetched copies of the live assets (see Pitfall 1). This rules out an entire category of suspected causes: stale deploy, GitHub Pages caching skew, base-path misconfiguration, CORS/`crossorigin` blocking, and CSS/JS minification stripping or reordering anything semantically. `access-control-allow-origin: *` is present on every asset response, `base: '/teaching-toddlers-typing/'` resolves correctly, and hand-tracing the CSS cascade/z-index math for `body::before`/`::after` (z-index -2) and `#star-trail` (z-index -1) against `#app` (`position: static`, so it paints *above* both per the CSS stacking-context spec) shows no structural defect — `#app`'s `background: transparent` should let both layers show through.

Because no code-level bug was found by static analysis, and because `.planning/STATE.md`'s own Deferred Verification table shows Phases 02, 02.1, and 03 were **never actually visually confirmed by a human in a real browser** before this playtesting round (`verification_deferred_human` for all three), the most defensible interpretation is that "verified in Phase 2/2.1" meant "matched the CSS/JS spec and passed automated build checks," not "a human watched it animate." The bug may be a genuine first-time-observed defect that requires live DevTools inspection this research pass cannot perform (no browser automation tool was available in this session), or it may be environment-specific — most plausibly `color-mix()` (used throughout the background/trail gradients) failing silently on an older browser on the family's actual device, which — per CSS's "invalid declaration is dropped in full" rule — would make the *entire* `background`/`box-shadow` declaration vanish, not just the color-mixed portion, exactly matching "not appearing" rather than "appearing but static." `color-mix()` is Baseline-widely-available (~93% global support, since 2023) so this is a secondary rather than primary hypothesis, but it is cheap, non-breaking insurance to add a plain-color fallback regardless of which hypothesis is correct.

**Primary recommendation:** Plan MENU-04/TRAIL-03 as a two-step sequence, not a single "find and fix" task: (1) a lightweight live-browser diagnostic (DevTools → Elements → Computed styles on `body::before` and `#star-trail`, plus a Console check for CSS parse warnings and a `matchMedia('(prefers-reduced-motion: reduce)')` check) to confirm which hypothesis is real, followed by (2) a defensive fix that adds a plain-color `background`/`box-shadow` fallback declaration ahead of every `color-mix()` use in `style.css` (a standard CSS cascade fallback — the browser uses the last value it understands) regardless of the diagnostic's outcome. For AUDIO-03, implement `LETTER_WORDS` exactly mirroring `DIGIT_WORDS`'s shape (Code Examples). For MENU-05, do **not** touch `#app`'s shared `justify-content: center` (it also governs the Settings/Stats panels) — instead give the new home-menu wrapper `margin-right: auto`, which opts that one flex item out of `justify-content` per the CSS Flexbox spec without touching the shared rule (Architecture Patterns). For DOCS-01, the edit is two single-line headings; a **separate, already-shipped** `keyboard-quest-settings` localStorage key was found in `src/settings-store.ts` during this research and is explicitly flagged as out of DOCS-01's locked scope (Runtime State Inventory) rather than silently fixed or silently ignored.

### Pattern 1: Flexbox `margin: auto` opt-out (MENU-05 left-alignment without touching shared `#app`)

**What:** `#app` is shared by the home menu AND the Settings/Stats panels (`src/main.ts` routes all of `menu`/`settings` through the same `#app` container). `#app`'s `justify-content: center` (`src/style.css:108-116`, `[VERIFIED: src/style.css:108-116]` — quoted: `"#app {\n  display: flex;\n  align-items: center;\n  justify-content: center;\n  min-height: 100vh;\n  background: transparent;\n  padding: max(16px, env(safe-area-inset-top)) ...\n}"`) must stay centered for Settings/Stats per CONTEXT.md's explicit scoping ("This left-alignment change applies to the home menu only"). Changing `#app`'s `justify-content` globally would incorrectly left-align Settings too.

**When to use:** Any time one flex child of a shared container needs to opt out of the container's `justify-content` without a container-level override or a second container.

**Example:**
```css
/* Source: CSS Flexbox spec — an auto margin on the main axis absorbs all
   free space for that item and excludes it from justify-content's
   alignment, per https://www.w3.org/TR/css-flexbox-1/#auto-margins */
.home-menu {
  /* One wrapper for the new title + the existing <nav class="menu">, so
     both inherit a single left-margin declaration (UI-SPEC's "Composition"
     requirement) instead of two that could drift apart. */
  display: flex;
  flex-direction: column;
  margin-left: max(64px, env(safe-area-inset-left)); /* 3xl token, mirrors #app's existing max(fixed, env()) pattern */
  margin-right: auto; /* opts this item out of #app's justify-content: center */
  row-gap: 32px; /* xl token — title-to-list gap per UI-SPEC */
}
```
`#app`'s own `justify-content: center` rule (`src/style.css:111`) is left completely untouched — Settings' `.settings-panel` has no auto margin, so it is unaffected and remains centered exactly as before. `[ASSUMED — pattern derived from CSS Flexbox spec, not from an external tutorial; verify visually in dev server before treating as final]`.

### Pattern 2: CSS cascade fallback for `color-mix()` (defensive fix for MENU-04/TRAIL-03)

**What:** Per the CSS parsing spec, a declaration containing one invalid function call is dropped **in its entirety** — not degraded to the valid parts. Every `background`/`box-shadow` in the drifting-background and star-trail rules uses `color-mix()` with no fallback, so on any browser that doesn't support it, that whole layer renders with *no* background/glow at all (fully invisible) rather than a flat, unmixed color.

**When to use:** Any CSS function without guaranteed universal support, when the visual absence-vs-presence gap matters (it does here — "not appearing" is exactly this failure mode).

**Example:**
```css
/* Source: CSS Cascade spec — the browser keeps the last declaration of the
   same property it understands; an unsupported later declaration is
   ignored and the earlier one stands. */
body::before {
  background: radial-gradient(circle at 30% 30%, var(--color-surface), transparent 60%),
              radial-gradient(circle at 70% 70%, var(--color-surface), transparent 60%); /* fallback: solid tint, no color-mix */
  background:
    radial-gradient(circle at 30% 30%, color-mix(in srgb, var(--color-surface) 10%, transparent), transparent 60%),
    radial-gradient(circle at 70% 70%, color-mix(in srgb, var(--color-surface) 10%, transparent), transparent 60%);
  background-size: 150% 150%;
  animation: drift-a 40s ease-in-out infinite alternate;
}
```
`[ASSUMED — defensive engineering recommendation; color-mix() itself is Baseline-widely-available since 2023 per caniuse (~93% global), so this specific gap is a secondary rather than primary hypothesis — see Pitfall 2]`.

### Anti-Patterns to Avoid
- **Fixing MENU-04/TRAIL-03 by adding a second CSS override or a JS-driven inline style:** the existing `data-chrome` gating mechanism is the single source of truth per CONTEXT.md ("any fix to background/trail visibility should stay within this existing mechanism, not introduce a second one"). A fix that works around the mechanism rather than through it will re-diverge the next time chrome state changes.
- **Reaching for `<say-as>`/SSML for AUDIO-03:** the browser `SpeechSynthesisUtterance` API takes plain text only — SSML markup is not supported by mainstream browser implementations and would just be read aloud as literal text. The explicit lookup-table pattern (mirroring `DIGIT_WORDS`) is the correct, already-proven-in-this-codebase approach.
- **Guessing at a fix for MENU-04/TRAIL-03 without a diagnostic step first:** given static analysis found no structural bug and the live bundle is confirmed identical to the local build, a blind code change risks being a no-op that doesn't address whatever the family's device actually shows. See Pitfall 1.

## Common Pitfalls

### Pitfall 1: Assuming the live deployment differs from the local build without checking
**What goes wrong:** Time gets spent hunting for a "deploy pipeline" bug (stale cache, base-path drift, minification stripping something) that doesn't exist.
**Why it happens:** "Works locally, broken live" strongly primes a build/deploy-difference hypothesis.
**How to avoid:** This research session built the project locally (`npm run build`) and diffed both `dist/assets/index-*.css` and `dist/assets/index-*.js` byte-for-byte against `curl`-fetched copies of the currently-live GitHub Pages assets — **they are identical.** `[VERIFIED: local build vs. curl https://halvorson.github.io/teaching-toddlers-typing/, this session]`. The live `index.html`'s asset hashes (`index-BQgTiJSK.js`, `index-CGJOWHWm.css`) match the fresh local build exactly. This means whatever the family observed is present in the *current committed source itself*, reachable via `npm run dev` too — it is not a deploy-specific artifact.
**Warning signs:** If a future "works locally, not live" report recurs, repeat this diff first (`npm run build` + `curl` the live JS/CSS + `diff`) before writing any fix code — it takes under a minute and immediately rules out an entire class of hypotheses.

### Pitfall 2: `color-mix()` silently dropping the whole declaration on unsupported browsers
**What goes wrong:** A `background`/`box-shadow` value containing one `color-mix()` call that the browser doesn't understand doesn't degrade gracefully to a "close enough" color — the entire declaration is invalid and ignored, so the element renders with *no* background/glow at all.
**Why it happens:** CSS's declaration-level (not function-level) validity rule is easy to forget; every visual layer in this phase's scope (`body::before`/`::after`, `.star-trail__star`, `.toggle-switch`, `#app.incorrect-flash`) uses `color-mix()` with no fallback.
**How to avoid:** Add an earlier, plain-color fallback declaration for the same property ahead of every `color-mix()` use (Architecture Patterns, Pattern 2) — cheap, zero-JS insurance regardless of whether this is the actual root cause on the family's device.
**Warning signs:** `color-mix()` support is Baseline-widely-available (~93% global, supported since Chrome 111 / Firefox 113 / Safari 16.2, roughly since 2023) `[CITED: caniuse.com/css-color-mix via WebSearch aggregation]` — so treat this as a secondary hypothesis, not a certainty, unless the diagnostic step (Pitfall-1-style live inspection) confirms `color-mix()` support is actually missing on the specific device in question.

### Pitfall 3: Reasoning about `speakTarget()`'s "Capital E" bug from the API spec instead of the actual voice behavior
**What goes wrong:** The Web Speech API spec itself does not document a "prepend Capital to bare uppercase letters" behavior — this is a per-voice/per-OS implementation detail (some accessibility-oriented or screen-reader-derived voices announce case explicitly when reading a single character, a convention borrowed from screen-reader "spelling mode"), not a documented cross-browser bug with a canonical citation.
**Why it happens:** Searching for an authoritative source describing this exact quirk turns up nothing definitive — MDN's `SpeechSynthesisUtterance` docs don't mention it, and no W3C bug tracker issue was found matching it precisely this session.
**How to avoid:** Treat CONTEXT.md's diagnosis (already a locked decision) as the working theory and implement the `LETTER_WORDS` fix regardless — spelling out the word (`'E' → 'Ee'`) sidesteps the ambiguity entirely rather than depending on understanding exactly which voice does what.
**Warning signs:** If after the `LETTER_WORDS` fix the child's device still says something unexpected (e.g., "Ee" spoken oddly), that's a signal the specific voice/OS combination needs direct listening verification — flag as a manual QA step, not something `tsc`/`vite build` can catch.

### Pitfall 4: `utterance.lang` silently resolving to `"en"` instead of `"en-US"`
**What goes wrong:** `speakTarget()`'s fallback `utterance.lang = document.documentElement.lang || 'en-US'` (`src/audio.ts:166`, `[VERIFIED: src/audio.ts:166]`, quoted: `"utterance.lang = document.documentElement.lang || 'en-US'"`) never actually falls back, because `index.html`'s `<html lang="en">` (`[VERIFIED: index.html:2]`, quoted: `<html lang="en">`) already supplies a truthy value — so `utterance.lang` is always the bare `"en"`, not `"en-US"`. Voice-matching logic then does `cachedVoices.find(candidate => candidate.lang.toLowerCase().startsWith(langPrefix))` where `langPrefix` is `utterance.lang.slice(0,2)` — `"en"` either way, so this specific line doesn't change voice selection. But `utterance.lang = "en"` itself (a bare language tag with no region) is passed directly to the synthesis engine and could influence which regional accent/dialect some engines choose for the *fallback* case where no matching cached voice is found.
**Why it happens:** The `|| 'en-US'` fallback was presumably written assuming `document.documentElement.lang` might be empty, not realizing it's always set.
**How to avoid:** Not part of this phase's locked scope (AUDIO-03 only covers the "Capital" fix) — flagged here as a secondary, non-blocking observation for awareness, not a required fix.
**Warning signs:** None currently observed as user-facing; only relevant if a future pronunciation-accent report surfaces.
