## Warnings

### WR-05: `mountMenu()` isn't defensively idempotent, unlike `mountGameScreen()` and `mountSettingsScreen()`

**File:** `src/menu.ts:223-227`

**Issue:** Every other screen-mount function in this codebase calls its own unmount function at the very top for idempotency:
- `game-screen.ts:55` — `mountGameScreen()` starts with `unmountGameScreen()`.
- `settings.ts:28` — `mountSettingsScreen()` starts with `unmountSettingsScreen()`, and the module's header comment explicitly states it "[m]irrors game-screen.ts's idempotent mount-calls-its-own-unmount lifecycle."

`mountMenu()` does not follow this pattern — it only bumps `mountGeneration`, resets `sharePending`, and calls `container.replaceChildren()`:

```ts
export function mountMenu(container: HTMLElement, handlers: MenuHandlers): void {
  mountGeneration++ // invalidate any in-flight runShare() from a prior mount
  sharePending = false // a stale in-flight call from the previous mount no
                        // longer blocks Share on this mount
  container.replaceChildren()
  ...
```

`container.replaceChildren()` wipes the DOM subtree, but it does **not** reset `copiedTimeoutId` or remove/null `shareFallbackEl` — those are only cleared inside `unmountMenu()` and `resetShareFeedback()`. If `mountMenu()` is ever invoked twice back-to-back without an intervening `unmountMenu()` call (currently prevented only by `main.ts`'s routing discipline, not by any guard in this module), a pending "Copied!" revert timer from the first mount survives into the second mount. Because `showCopiedFeedback()`'s `setTimeout` callback reads the *module-level* `shareLabelEl` variable (not a closed-over snapshot), and `shareLabelEl` gets reassigned to the new mount's `<span>` partway through the second `mountMenu()` call, the stale timer will fire against the **new** mount's Share label and silently revert it to "Share" — even if the new mount's own, unrelated Share interaction is mid-flight showing "Copied!" or a manual-fallback panel. The old mount's detached `nav` element also keeps its four listeners (`click`/`keydown`/`mouseover`/`focusin`) attached and unreachable rather than explicitly removed.

This does not currently manifest as a user-visible bug because `main.ts`'s `mountScreen()` always unmounts whatever `currentScreen` is before mounting the next one. It is flagged because it silently breaks the "mount is idempotent" contract this module's sibling files rely on and document, making the module fragile to any future caller (a second entry point, a hot-reload path, a test harness) that mounts the menu without perfectly mirroring `main.ts`'s discipline.

**Fix:** Call `unmountMenu()` at the top of `mountMenu()`, matching `mountGameScreen()`/`mountSettingsScreen()`:

```ts
export function mountMenu(container: HTMLElement, handlers: MenuHandlers): void {
  unmountMenu()
  mountGeneration++ // invalidate any in-flight runShare() from a prior mount
  sharePending = false
  container.replaceChildren()
  ...
```
(Note `unmountMenu()` already increments `mountGeneration` and resets `sharePending` itself, so the follow-up `mountGeneration++`/`sharePending = false` lines become redundant-but-harmless double resets, or can be dropped once `unmountMenu()` is guaranteed to run first — either is safe.)

### IN-01: `.menu-label` class applied in JS has no corresponding CSS rule

**File:** `src/menu.ts:292`, `src/style.css` (no matching selector exists)

**Issue:** The Share row's label `<span>` is given `className = 'menu-label'` (`src/menu.ts:292`), but `style.css` has no `.menu-label` rule anywhere (confirmed via search across `src/*.css`). It renders correctly only because it inherits `color`/`font-family`/`font-weight` from the parent `.menu-item` button. Not a functional defect, but a styling hook that doesn't exist reads as either dead code or a forgotten rule. Unchanged from prior reviews; not in scope for any fix iteration so far.

**Fix:** Either add an (even empty/documented) `.menu-label { }` rule in `style.css` for clarity, or drop the class from the span if it's not intended to be a styling hook.

### IN-03: `handleClick`'s branch chain silently no-ops for the `stats` row with no exhaustiveness check

**File:** `src/menu.ts:309-327`

**Issue:** `handleClick` branches with `if (isGameplayRow(row)) ... else if (row === 'quit') ... else if (row === 'share') ... else if (row === 'settings') ...` and falls through to nothing for `row === 'stats'`, relying on a trailing comment ("stats stays undispatched") rather than a compiler-enforced exhaustiveness check. Intentional per the comment (Phase 4 owns that screen) and not a bug today, but `MenuRow` isn't switched over exhaustively, so a future new row value added to `MENU_ROWS` without a corresponding branch would silently no-op with no type-level warning. Unchanged from prior reviews.

**Fix:** Optional — convert to a `switch (row)` with a `default` branch asserting `row` is `never` (or an explicit `stats` case with a comment) to get a compile-time reminder whenever `MenuRow` gains a new member.

### IN-04: Share label briefly flickers back to "Share" on a click made while a previous copy request is still in flight

**File:** `src/menu.ts:319-321`

**Issue:** `handleClick`'s Share branch unconditionally calls `resetShareFeedback()` before `runShare()` on every click, regardless of `sharePending`:

```ts
} else if (row === 'share') {
  resetShareFeedback()
  void runShare()
}
```

`runShare()` itself no-ops immediately when `sharePending` is already `true` (`src/menu.ts:199`), but `resetShareFeedback()` has already run by that point and will have reverted the label to "Share" (and torn down any visible manual-fallback panel) even though no new copy attempt actually started. For the common fast path (Clipboard API resolving in a few milliseconds) this window is imperceptible. But if `shareCurrentUrl()`'s `navigator.clipboard.writeText()` is blocked on a browser permission prompt (a real, documented possibility per `clipboard.ts`'s own comments) and a parent double-taps the Share row while that prompt is open, the visible "Copied!"/fallback state from the first click will flash away and only reappear once the original request resolves — a minor, easily-confusable-with-broken cosmetic glitch, not a functional failure.

**Fix:** Guard the reset with the same flag `runShare()` already checks, e.g. only call `resetShareFeedback()` when `!sharePending`, or move the reset inside `runShare()` itself immediately after the `sharePending` early-return check so a blocked concurrent click is a true no-op with zero visible side effect.
