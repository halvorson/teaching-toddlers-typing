<objective>
Make a correct key press *sound* like a win: a short synthesized chime plus the spoken name of the
letter or digit that was just matched, both switchable off from a new Sound toggle on the Settings
screen that remembers its state.

Purpose: AUDIO-01, AUDIO-02, SET-01. The celebration loop is this project's Core Value; today it
is entirely silent. This plan adds the audio half of it without adding a single npm package, a
single audio asset, or a single new CSS rule.
Output: `src/audio.ts` (new), an extended `AppSettings` record, two new calls in the existing
correct-match branch, and a second toggle row in the Settings panel — plus a fix for the
full-replace `writeSettings` bug that Phase 2.1 left behind and that this phase's second field
would otherwise expose.
</objective>

## Planning Decision — one `audio.ts`, two independent entry points

CONTEXT.md leaves module layout to discretion. Resolved here: **one** module, `src/audio.ts`,
exporting exactly two functions, `playChime()` and `speakTarget(character)`. They share the file
and nothing else — no shared queue, no shared state, no sequencing, no awaiting each other. That
independence is a hard requirement (a speech failure must never suppress the chime and vice
versa), and the cheapest way to guarantee it is two separate `try` blocks with two separate
`readSettings().soundEnabled` gates, mirroring how `celebrate.ts` puts its one guard inside its
one chokepoint rather than at the call sites.

## Planning Decision — which toggle was clicked is read from `data-setting`

`settings.ts` has a single delegated `handleClick` and both toggle rows will share the
`.toggle-switch` class, so the handler must tell them apart. Resolved here: each toggle button
carries a `dataset.setting` value (`'resetTrailOnMistake'` / `'soundEnabled'`) and `handleClick`
branches on it with an explicit if/else that names both fields literally. Not an `aria-label`
string comparison (that couples persistence to display copy) and not a computed object key (that
would let a DOM-sourced string choose which field of the persisted record to write).

**`src/audio.ts` — new module.**
Open it with a doc comment in `celebrate.ts`'s style that names this module's three conventions:
one lazily created, reused `AudioContext`; `readSettings().soundEnabled` re-read at the top of
every exported function rather than cached; and every browser-API call wrapped in a
comment-only-`catch` because audio here is decorative and the game must keep working without it.
Import `readSettings` from `./settings-store`. Nothing else is imported.

- Module-level `let audioCtx: AudioContext | null = null`.
- Module-private `function getAudioContext(): AudioContext` — when `audioCtx` is null, assign
  `audioCtx = new AudioContext()`; then, when `audioCtx.state === 'suspended'`, call
  `void audioCtx.resume()` (fire-and-forget: this only ever runs inside a keydown handler, which
  is already the qualifying user gesture, so no unlock UI exists or is needed). Return `audioCtx`.
  This function is the module's only construction site for the context. Browsers cap how many live
  contexts one page may hold; building one per key press exhausts that cap within a minute of
  toddler play and the chime then dies mid-session with no visible symptom. Individual oscillator
  and gain nodes are one-shot and *are* created per play — only the context is the singleton.
- Module-private `const PEAK_GAIN = 0.12` — a gentle accent under the muted celebration, not a
  loud alert.
- Module-private `function playTone(ctx: AudioContext, freq: number, startTime: number, duration: number): void`.
  Create an oscillator via `ctx.createOscillator()` and a gain via `ctx.createGain()`. Set the
  oscillator's `type` to `'sine'` (soft, no bright harmonics) and schedule its pitch with
  `osc.frequency.setValueAtTime(freq, startTime)`. Connect oscillator → gain → `ctx.destination`.
  Shape the envelope **only** through the AudioParam scheduling methods —
  `setValueAtTime(0, startTime)`, then `linearRampToValueAtTime(PEAK_GAIN, startTime + 0.015)` for
  a 15 ms attack, then `exponentialRampToValueAtTime(0.0001, startTime + duration)` for the decay.
  Never assign the gain param's `value` property directly for any part of the envelope: an
  instantaneous amplitude jump is audible as a click or pop and would wreck the muted character
  the celebration palette is built around. The exponential ramp targets `0.0001` rather than zero
  because an exponential curve cannot reach zero. Call `osc.start(startTime)` and
  `osc.stop(startTime + duration + 0.02)`, and in an `osc.onended` handler call `osc.disconnect()`
  and the gain node's `disconnect()` so nodes do not accumulate across a long session.
- `export function playChime(): void` — first line is the gate:
  `if (!readSettings().soundEnabled) return`. Read fresh on every call, never cached at module
  scope, so flipping the toggle in Settings takes effect on the very next correct match with no
  reload (the same reasoning `game-screen.ts` already documents for the trail-reset read). Then a
  single `try` block: get the context, take `const now = ctx.currentTime`, and fire two ascending
  notes — `playTone(ctx, 659.25, now, 0.14)` and `playTone(ctx, 987.77, now + 0.085, 0.2)`. That is
  E5 up to B5, roughly 285 ms end to end, short and soft enough to sit under the confetti rather
  than over it. Close with a comment-only `catch` — no logging call of any kind, matching every
  other swallowed failure in this codebase.

**`src/audio.ts` — voice cache, digit words, and `speakTarget`.**

- Module-level `let cachedVoices: SpeechSynthesisVoice[] = []`.
- Module-private `function primeVoices(): void`, wrapped in `try` with a comment-only `catch`.
  Return early when `window.speechSynthesis` is absent. Otherwise assign
  `cachedVoices = window.speechSynthesis.getVoices()` **synchronously**, and *also* register
  `window.speechSynthesis.addEventListener('voiceschanged', ...)` with `{ once: true }`, whose
  handler re-assigns `cachedVoices` from `getVoices()` again. Both halves are required and neither
  is sufficient alone: Chrome loads voices asynchronously and returns an empty array from the
  synchronous call, while Firefox and Safari load them synchronously and may never fire the event
  at all. Call `primeVoices()` once at module scope. `audio.ts` is statically imported by
  `game-screen.ts`, so this runs at page load — which is the "cache at startup" the stack guidance
  asks for, with no extra bootstrap wiring in `main.ts`.
- Module-private `const DIGIT_WORDS: Readonly<Record<string, string>>` mapping each of the ten
  members of `game.ts`'s `DIGITS` pool to its English word: `'0': 'zero'`, `'1': 'one'`,
  `'2': 'two'`, `'3': 'three'`, `'4': 'four'`, `'5': 'five'`, `'6': 'six'`, `'7': 'seven'`,
  `'8': 'eight'`, `'9': 'nine'`. Declare it here, not in `game.ts`: `game.ts` owns character
  *pools*, `audio.ts` owns how a matched character is *pronounced*. A bare digit glyph is not a
  pronunciation the Speech API guarantees across voices — some read it as the number, some spell
  or inflect it oddly — and one hard-coded lookup removes the ambiguity for ten lines of code.
  Uppercase A-Z needs no mapping: English voices read a bare capital letter as its letter name.
- `export function speakTarget(character: string): void` — first line is its own gate,
  `if (!readSettings().soundEnabled) return`, a second independent read rather than a value shared
  with `playChime`. Then a single `try` block:
  - `const spoken = DIGIT_WORDS[character] ?? character` — digits become words, letters pass
    through unchanged.
  - Return early when `window.speechSynthesis` is absent.
  - Call `window.speechSynthesis.cancel()` before speaking, so a fast run of correct matches never
    queues utterances that fall behind the character actually on screen. Note for the executor and
    for QA: on some browser/OS combinations a `cancel()` immediately followed by `speak()` silently
    drops the new utterance. That is a known, still-open browser quirk, it is already absorbed by
    this module's silent-degrade contract, and "speech occasionally didn't fire" is therefore an
    accepted characteristic — not a bug to chase, and not a reason to add a timer between the two
    calls, which would reintroduce exactly the latency the fire-and-forget decision rules out.
  - Construct a fresh `new SpeechSynthesisUtterance(spoken)` on every call — an utterance object is
    not reliably reusable once it has been spoken, so there is no module-level utterance to cache.
  - Set `utterance.lang` from `document.documentElement.lang || 'en-US'`, leave `rate` and `pitch`
    at their defaults, and pick a voice from the cache: prefer the entry whose `default` flag is
    set, otherwise the first entry whose `lang` (lowercased) starts with the two-letter prefix of
    the document language. Assign `utterance.voice` only when a match was found; leaving it unset
    is the correct fallback and lets the browser choose. There is no voice-picker UI in this phase.
  - `window.speechSynthesis.speak(utterance)` and return immediately — nothing is awaited and
    nothing about the target swap waits on this.
  - Comment-only `catch`, no logging.
- Extend the module doc comment to name the second entry point and state that the two are
  independent by construction.
