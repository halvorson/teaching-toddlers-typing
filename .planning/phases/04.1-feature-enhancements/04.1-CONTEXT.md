# Phase 4.1: Feature Enhancements - Context

**Gathered:** 2026-08-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Parents get more control over three things — celebration sound, fullscreen behavior, and
session length — and Quit's confusing role on the home menu is resolved (SET-03, MENU-06,
FULL-04, SESSION-01..04). Specifically: the binary sound toggle becomes a 3-state control
(Off/Chime/Spoken letter), a new Settings toggle controls auto-fullscreen-on-launch, a new
Settings control caps session length by correct-match count (applying to Letters, Numbers,
and Alphabet modes), reaching that cap (or Z in Alphabet mode, whichever comes first) ends
the session with the existing bigger celebration followed by a new Game Over/Congrats screen
offering a "One more letter" override, and the home menu's Quit row is removed entirely.

</domain>

<decisions>
## Implementation Decisions

### Quit (MENU-06)
- **D-01:** The home menu's Quit row is removed entirely, along with its `menu-group--quit`
  wrapper group. Investigation during discussion found it was already a functional no-op:
  `menuHandlers.onQuit()` → `quitToMenu()` in `main.ts` early-returns when
  `currentScreen === 'menu'`, which is always true when the Quit row is clicked (it only
  exists on the home menu itself) — there is no real "quit a webpage" action JS can perform.
  In-game "leave to menu" continues to work via the existing Escape handler (`onQuit`
  callback passed to `mountGameScreen`/`mountSettingsScreen`), and gets a visible on-screen
  back control in Phase 4.2 (MOBILE-02) — this phase does not need to touch that path.
- **D-02:** `MenuRow`'s `'quit'` member, `MENU_LABELS.quit`, and the `groupQuit` DOM
  construction in `menu.ts` are removed as part of this row's removal (not just visually
  hidden) — **Reversibility:** reversible — small, self-contained deletion; easy to re-add if
  ever needed.

### 3-State Sound Control (SET-03)
- **D-03:** The three states are **mutually exclusive**, not additive: Off = silent, Chime =
  chime only (no speech), Spoken letter = speech only (no chime). This replaces
  `soundEnabled: boolean` in `AppSettings` with a `soundMode: 'off' | 'chime' | 'spoken'` field
  (exact type name is Claude's discretion) — **Reversibility:** costly — every
  `readSettings().soundEnabled` call site (`game-screen.ts`'s chime/speech trigger,
  `settings.ts`'s toggle read) and the `AppSettings` shape-check in `settings-store.ts` need
  updating together; a future revert would need a migration path for already-persisted
  `soundEnabled` values (see D-05).
- **D-04:** Default state is **Chime** (not Spoken letter) — chime is the sound most directly
  tied to the Core Value's "immediate, delightful, low-stakes celebration" instant-feedback
  loop; speech is a secondary teaching layer. This is the closest single-state equivalent to
  today's on-default per SET-03's "still... defaulting to the equivalent of today's on-state"
  wording, since today's ON plays chime+speech together and a mutually-exclusive control
  can't reproduce that exactly.
- **D-05:** Migration from the existing persisted `soundEnabled: boolean` field: an existing
  `soundEnabled: true` record should resolve to `soundMode: 'chime'` (matches D-04's default
  reasoning) and `soundEnabled: false` should resolve to `soundMode: 'off'`, following the
  same per-field default-on-invalid-type pattern `settings-store.ts` already uses for
  `soundEnabled` itself (a Phase 3 record with no `soundEnabled` field loads cleanly with a
  default). Exact migration code is Claude's discretion, but some persisted-field migration
  must exist — this is not optional cleanup.
- **D-06:** UI shape is a **3-segment control**: one row with 3 side-by-side segments/buttons
  (Off | Chime | Spoken), one visibly active at a time, any segment directly tappable —  not
  a cycling single button, not 3 stacked toggle-switch rows. This is a new component
  replacing the existing `role="switch"` toggle-switch markup for the sound row specifically
  (the `resetTrailOnMistake` toggle row is unaffected and keeps its existing binary
  `.toggle-switch` markup).
- **D-07:** **Build the segmented control as a reusable, N-option component** — not
  hardcoded to exactly 3 segments. The session-cap control (D-09) reuses the same component
  shape with 4 options, so the segmented-control implementation must accept a variable list
  of `{value, label}` options rather than assuming 3. This was an explicit, direct user
  instruction, not Claude's inference — **Reversibility:** reversible, but do not skip: two
  independent hand-rolled segmented controls instead of one shared component would be a
  direct violation of what was asked.

### Fullscreen Toggle (FULL-04)
- No open gray areas surfaced during discussion — requirement text is unambiguous: a new
  Settings toggle controls whether starting a mode auto-enters fullscreen, defaulting to on
  (today's behavior). Reuses the existing `.toggle-switch` binary pattern (same shape as the
  `resetTrailOnMistake` row), extends `AppSettings` with a new boolean field. See Claude's
  Discretion below for the one implementation nuance (does toggling it off while already
  fullscreen exit immediately, or only affect the next mode launch).

### Session Length Cap (SESSION-01..04)
- **D-08:** Cap control input shape is the **same reusable N-segment control** introduced for
  sound (D-06/D-07), not a stepper, slider, or free-form number field — keeps the app's one
  segmented-control component doing double duty and avoids introducing a second, differently-
  shaped input pattern into Settings.
- **D-09:** Cap control has **exactly 4 options: 10 / 26 / 50 / No Cap**. 26 was chosen
  specifically because it equals one full lap of the alphabet (explicit user reasoning, not
  Claude's inference) — this value is meaningful for Alphabet mode in particular, not an
  arbitrary round number. "No Cap" is a real 4th segment, not merely the highest number —
  selecting it restores today's uncapped, session-never-interrupted behavior.
- **D-10:** **Default cap value is 50.**
- **D-11:** The correct-match counter that this cap compares against resets whenever a mode
  is (re-)entered (SESSION-03, already explicit in ROADMAP.md — restated here since it's
  load-bearing for D-12's "new session" definition below).
- **D-12 (Game Over screen, SESSION-02):** The Game Over/Congrats screen is
  **full-immersive** — a big centered message filling the screen (matching the scale of the
  target-letter display and the bigger celebration that just played), **not** a windowed
  panel in the style of Settings/Stats. Rationale (explicit from discussion): this is a
  genuine milestone moment for the child, not a parent-facing utility screen.
- **D-13:** The Game Over/Congrats screen has **exactly two actions**: "One more letter"
  (the SESSION-04 override) and "Back to menu." No separate "Play again / restart this mode"
  action — explicitly rejected in favor of the simpler two-action screen.
- **D-14 (the load-bearing "one more letter" mechanic, SESSION-04):** Using "One more letter"
  does **not** just extend the session by exactly one more correct match. It **removes the
  cap entirely for the remainder of that session** — e.g. with a configured cap of 26,
  hitting it once and choosing "One more letter" means the session can continue uninterrupted
  past 26, 50, 200, or any further count without the Game Over screen reappearing. The
  configured cap (e.g. 26) is restored from scratch only when a **new session** begins — i.e.
  when the player returns to the menu and (re-)enters a mode (ties directly to D-11's
  counter-reset trigger). This was an explicit correction from the user during discussion —
  do not implement "one more letter" as "add exactly 1 to the effective cap and re-check on
  the very next match," which was the initial literal reading of SESSION-04's wording.
  **Reversibility:** costly — this is genuine session-scoped state distinct from the
  persisted cap setting (a boolean like `capOverriddenThisSession`, reset alongside the match
  counter on mode entry) rather than a Settings-store field; changing this behavior later
  means introducing new state shape, not just flipping a default.
- **D-15 (Alphabet mode interaction):** Per SESSION-02's own wording ("reaching the cap — or,
  in Alphabet mode, reaching Z, whichever comes first"), Alphabet mode's existing Z-completion
  behavior (`celebrateAlphabetComplete()`, then loop back to A) is superseded by the Game Over
  flow when the cap has already been reached or is reached at exactly the same match as Z. No
  new decision needed here beyond reusing the existing bigger-celebration function per
  SESSION-02's explicit instruction — this row exists to flag the interaction point for the
  planner, not to introduce new scope.

### Claude's Discretion
- Exact TypeScript field/type names (`soundMode` vs. alternatives, the exact cap-setting field
  name, the exact session-override-flag name/location).
- Whether toggling the fullscreen-default setting off while a mode is already running in
  fullscreen exits fullscreen immediately, or only takes effect on the next mode launch —
  requirement text only specifies the default-on behavior, not this edge case. Recommend:
  only affects the next launch (consistent with `fullscreen.ts`'s existing fire-and-forget,
  never-gates-navigation philosophy), but this is not locked.
- Exact visual treatment/animation/copy for the Game Over/Congrats screen (message wording,
  layout details within "full-immersive, matches celebration scale") — no specific text was
  given.
- Internal module/file layout (e.g. whether the segmented-control component lives in a new
  shared file or inline where first used; whether Game Over gets its own module mirroring
  `settings.ts`'s mount/unmount lifecycle, which is the established pattern to follow
  regardless of file name).
- Migration code shape for D-05 (`soundEnabled` → `soundMode`).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/settings-store.ts` — the versioned, shape-checked-read, silent-degrade-write
  `AppSettings` pattern (`readSettings()`/`writeSettings()`) this phase extends with
  `soundMode`, the fullscreen-default toggle, and the session-cap value — same key
  (`keyboard-quest-settings`), same `version: 1`, same per-field-default-on-invalid-type
  resolution already established for `soundEnabled` (Phase 3) and now needed for D-05's
  migration.
- `src/settings.ts` — `mountSettingsScreen()`'s delegated-click-listener,
  `dataset.setting`-branching, merge-write (`writeSettings({ ...readSettings(), field: next })`)
  pattern is the direct model for wiring up the new segmented controls (sound, cap) and the
  new fullscreen toggle row. The existing `.toggle-switch`/`role="switch"` binary pattern
  stays as-is for the fullscreen toggle and the untouched `resetTrailOnMistake` toggle.
- `src/celebrate.ts` — `celebrateAlphabetComplete()` is the "existing bigger celebration"
  SESSION-02 explicitly says to reuse for cap-completion, not a new celebration to design.
- `src/game-screen.ts` — the correct-match branch (`currentTarget`/`selectNext` flow) is
  where the correct-match counter, cap comparison, and Game Over trigger all need to hook in;
  the module already tracks `currentTarget` as module-level state, so a match counter and a
  session-override flag are a natural sibling addition at the same scope.
- `src/menu.ts` — `MENU_ROWS`/`MENU_LABELS`/`GAMEPLAY_ROWS`/`UTILITY_ROWS` and the
  `groupPrimary`/`groupUtility`/`groupQuit` DOM construction in `mountMenu()` are exactly
  what D-01/D-02's Quit removal touches — delete the `'quit'` member, its label, and the
  `groupQuit` div/branch, and remove `onQuit` from `MenuHandlers` if nothing else calls it
  (confirm during planning whether `main.ts`'s `quitToMenu` is called from anywhere besides
  the now-removed menu row and the existing Escape/fullscreenchange paths — it is, so
  `quitToMenu()` itself stays; only the menu row and `MenuHandlers.onQuit` wiring for it
  goes away).

### Established Patterns
- Fresh-read-per-call for settings (no caching at mount) — `game-screen.ts`'s existing
  `readSettings().resetTrailOnMistake` read is the direct precedent for reading `soundMode`,
  the fullscreen-default toggle, and the cap value the same way.
- Merge-write on every `writeSettings()` call (`{ ...readSettings(), field: next }`) —
  established in Phase 3 specifically to prevent one toggle's write from clobbering another
  field; the new segmented controls must follow this same merge pattern.
- `textContent`-only DOM construction, never `innerHTML`, codebase-wide invariant — applies
  to the new segmented-control component and the new Game Over screen module alike.
- Silent-degrade-on-failure for all decorative/utility/persistence code — no error UI
  anywhere in this codebase; the new settings fields follow the same silent-degrade contract
  as every existing field.

### Integration Points
- `game-screen.ts`'s correct-match branch — cap comparison, session-override flag, and Game
  Over trigger all join here, alongside the existing celebration/trail/chime/speech calls.
- `settings-store.ts`'s `AppSettings` interface — gains `soundMode`, a fullscreen-default
  boolean, and a cap-value field; loses nothing (no field removal, per the migration in D-05).
- `settings.ts` — gains the new segmented-control rows (sound, cap) and the new fullscreen
  toggle row, alongside the existing `resetTrailOnMistake` toggle.
- `menu.ts` — loses the Quit row/group; `MenuHandlers` interface loses `onQuit` if confirmed
  unused elsewhere per the note above.
- A new module for the Game Over/Congrats screen (name/location is Claude's discretion),
  mounted from `main.ts`'s screen-switching logic analogous to how `settings`/`stats` screens
  are mounted, triggered from `game-screen.ts` when the cap (or Z) is reached.

</code_context>

<specifics>
## Specific Ideas

- The number 26 for the mid-tier cap option is deliberate: "26 gets us through one lap of the
  alphabet" — an explicit, meaningful choice tied to Alphabet mode, not an arbitrary round
  number picked for its own sake.
- "One more letter" should behave like a genuine "one more turn" mechanic: using it removes
  the cap for the rest of the current session entirely (not a one-shot "+1" extension), and
  the configured cap only comes back into effect on the next fresh session (menu → re-enter a
  mode). See D-14 — this is the single most load-bearing, non-obvious decision in this phase.
- The segmented-control component must be built reusable across the sound control (3 options)
  and the session-cap control (4 options) — an explicit, direct build instruction from the
  user (D-07), not an optional nice-to-have.

</specifics>
