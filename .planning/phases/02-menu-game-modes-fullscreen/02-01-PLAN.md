<objective>
Replace Phase 1's single hardcoded Letters loop with the real product shell: a home menu is the app's
entry point, the three gameplay rows launch a mode-parameterized game screen in fullscreen, and every
exit path — Escape, the Quit row, or an unexpected fullscreen exit — lands back on the menu. Letters
mode is the tracer path proven end-to-end first; Numbers mode is the second slice through the same
machinery.

Purpose: this is the phase's architectural spine. Every other Phase 2 plan (menu chrome, Alphabet
mode, Share, windowed panels) hangs off the router, the mount/unmount switch, and the single
quit-to-menu function created here. Getting the fullscreen-exit resync right here is what keeps the
app from stranding a parent on a game screen with no keyboard way out (02-RESEARCH.md Pitfall 1).

Output: `src/router.ts`, `src/fullscreen.ts`, `src/menu.ts`, `src/game-screen.ts` (new); a rewritten
`src/main.ts`; a generalized `src/game.ts`; menu base styling in `src/style.css`.
</objective>

<assumption_delta_decision>
**Noun:** "game mode" — singular→plural transition (Phase 1 had exactly one hardcoded Letters loop;
Phase 2 has three).
**Decision:** PROMOTE. The generalized, pool-and-strategy-parameterized loop becomes the primary
representation, and Phase 1's Letters behaviour becomes one configuration of it. Phase 1's
`pickTarget()`/`targetCode()` are not kept alongside the general functions as a second code path —
they are replaced by `pickRandom(pool, exclude)` and `letterCode(letter)`, and every call site moves.
**Rationale:** adding Numbers/Alphabet beside a still-hardcoded Letters loop would create three
divergent match paths and three places for the physical-key-code bug (02-RESEARCH.md Pitfall 2) to
hide. One parameterized loop has exactly one match path to verify.
</assumption_delta_decision>

    Generalize `src/game.ts` first (D-19, the assumption-delta promotion). Replace `pickTarget` with
    `pickRandom(pool, exclude?)`, which keeps Phase 1's structural exclusion — filter the excluded
    member out of the candidate pool and index into that filtered pool, never retry in a loop — but
    takes the pool as a parameter. Replace `targetCode` with `letterCode(letter)`, which returns a
    readonly array of the acceptable physical-key identifiers for that letter (a single element,
    formed by prefixing `Key` to the uppercase letter). Add `acceptableCodes(target, mode)`, which is
    the one function every mode's match check goes through; for this task it returns `letterCode(target)`
    for all modes and Task 2 adds the digit branch. Keep `LETTERS` and `renderTarget` exactly as they

    Create `src/router.ts` (D-19). Export the `Screen` union and a module-private frozen allow-list of
    its members. `readInitialScreen()` reads the search string through `URLSearchParams`, looks up the
    `screen` key, and returns it only if the allow-list contains it — anything else, including a
    missing key, returns `'menu'`. This allow-list check is the plan's input-validation control
    (T-02-01); a value that fails it must never reach the mount switch. `navigateTo(screen)` builds a
    `URL` from `window.location.href`, deletes the `screen` search param when the target is the menu
    (so the shared root URL stays clean) and sets it otherwise, then rewrites the current history entry
    in place with `history.replaceState`. It must never append a history entry — the Back button must
    not have to be pressed once per menu transition to leave the app.

    Create `src/fullscreen.ts` (D-09, D-10). `enterFullscreen(el)` feature-detects the request method
    with a `typeof … === 'function'` check, calls it, and attaches a `.catch()` that swallows the
    rejection with an explanatory comment. It returns `void` and is never awaited — a caller that
    awaited it would leave the game screen blank on iOS Safari, where the request is documented as
    failing without a reliably catchable rejection. `exitFullscreenIfActive()` checks
    `document.fullscreenElement` first and only then calls the document's exit method, again with a
    swallowed catch; when nothing is fullscreen it is correctly a no-op, and the caller still navigates.

    Create `src/menu.ts` (D-01, D-03). Export `MENU_ROWS` in the exact UI-SPEC order — letters,
    numbers, alphabet, stats, settings, share, quit — and `MENU_LABELS` mapping them to the exact
    case-sensitive strings `Letters`, `Numbers`, `Alphabet`, `Statistics`, `Settings`, `Share`, `Quit`.
    `mountMenu(container, handlers)` clears the container, creates a `nav` element with class `menu`,
    and for each row creates a real `button` element with `type="button"`, class `menu-item`, a
    `data-row` attribute carrying the row id, and its label assigned through the element's text-content
    property. Using a real button is what gives Enter and Space activation and touch activation for
    free. Group the rows into three `div` elements with classes `menu-group`, `menu-group--utility` and
    `menu-group--quit` so the 24px/24px/32px group gaps of the UI-SPEC layout have something to hang
    off. Register one delegated `click` listener on the nav that resolves the activated row from the
    closest button's `data-row` value and dispatches: the three gameplay rows call
    `handlers.onLaunchMode(row)`, `quit` calls `handlers.onQuit()`, and the remaining three rows are
    left undispatched in this plan — plan `02-04` adds their handlers when it delivers those screens.
    `unmountMenu()` removes the listener and empties the container; keep the listener reference in a
    module-level variable so removal is exact. Arrow-key navigation and the focus indicator are Task 2
    of plan `02-02`; this task only needs the rows to render and the mode rows to activate.

    Create `src/game-screen.ts`. `mountGameScreen(container, mode, onQuit)` clears the container,
    creates the `#target` span exactly as Phase 1's `main.ts` did, appends it, picks the first target
    with `pickRandom(LETTERS)` and renders it with `renderTarget`. It then registers one `keydown`
    listener on `document`, held in a module-level variable so `unmountGameScreen()` can remove exactly
    it. The handler's statements are ordered: the auto-repeat early return first (CORE-04, unchanged
    from Phase 1 — placing it later would let auto-repeat drive the incorrect branch); then a check for
    the semantic key name `Escape`, which calls `onQuit()` and returns (02-RESEARCH.md Pitfall 4 — the
    semantic name is the correct choice for action keys, and this early return is also what stops the
    quit keypress from firing a spurious neutral flicker on its way out); then the match check, which
    tests whether `acceptableCodes(currentTarget, mode)` contains the event's physical key code. Never
    compare against the property carrying the character the key produced — that varies with Shift, Caps
    Lock and layout and would break CORE-02. The correct branch, the incorrect branch, the pulse
    restart, the container flash restart and the `celebrate()` call are all lifted from Phase 1's
    `main.ts` verbatim in behaviour. `unmountGameScreen()` removes the keydown listener, empties the
    container, and drops the module state.

    Rewrite `src/main.ts` as the orchestrator (D-05, D-11). Resolve `#app` once. Hold `currentScreen`
    in a module-level variable. `mountScreen(screen)` unmounts whatever is currently mounted (switch on
    `currentScreen`), assigns the new `currentScreen`, calls `navigateTo(screen)`, sets
    `document.body.dataset.chrome` to `'menu'` for the menu and `'game'` for the three gameplay screens
    so the stylesheet can distinguish them, and mounts the new screen. `launchMode(mode)` calls
    `mountScreen(mode)` and then `enterFullscreen(document.documentElement)` — in that order, so the
    game screen and its first target are already on screen regardless of what the fullscreen request
    does (D-09, FULL-01). `quitToMenu()` is the single resync function required by 02-RESEARCH.md
    Pitfall 1: it calls `exitFullscreenIfActive()` unconditionally first (D-10, and this is what makes
    MENU-03 true even when the menu itself was fullscreened), then returns early if `currentScreen` is

    Do not request fullscreen on that initial boot call even when the URL names a mode — a page load is
    not a user activation and the request would be rejected; fullscreen is entered only from

    That gives `quitToMenu` two trigger sites — the fullscreenchange listener and the in-game Escape

    paths" requires. The direct Escape call is load-bearing, not redundant: where the fullscreen request
    silently failed there is no fullscreen state to change, so the event never fires and the event-only
    version would leave a parent stuck on the game screen.

    Extend `src/style.css`. Move the dominant background colour from the `#app` rule to a `body` rule

    margin, and the nav a 24px row gap. Add `overflow-y: auto` on the nav so seven rows can never be
    clipped unreachably on a short landscape viewport.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query string → app screen state | Untrusted, user- or link-supplied text that selects which screen the app mounts |
| Physical keyboard → game screen | The only gameplay input crossing into the application |
| App source → browser DOM | The single rendering path that could interpret a string as markup |
| Browser → native Fullscreen API | The app hands control of the viewport chrome to the platform |
