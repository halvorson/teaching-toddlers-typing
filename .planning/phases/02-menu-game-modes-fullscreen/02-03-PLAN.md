<objective>
Add the third game mode: Alphabet presents the letters in strict A→Z order through the same loop
Letters and Numbers already use, and completing Z fires a distinctly bigger three-burst celebration
before looping straight back to A.

Purpose: Alphabet mode is the one mode with a shape — it teaches sequence rather than recognition, and
the Z celebration is the only "you finished something" moment the whole app has. Getting it out of the
same confetti call as every other celebration is what keeps the app's celebration vocabulary
consistent rather than introducing a second animation system.

Output: `nextInSequence` in `src/game.ts`; a parameterized burst helper and `celebrateAlphabetComplete`
in `src/celebrate.ts`; the mode-aware selection strategy and the Z branch in `src/game-screen.ts`.
</objective>

  <action>
    Add `nextInSequence(pool, current)` to `src/game.ts`. It takes the current target as `string | null`
    and returns the pool's first member when passed null — that is how a mode gets its opening target —
    and otherwise finds the current member's index and returns the member one position later, wrapping
    the last position back to the first with a modulo. The wraparound is unconditional: after Z it
    returns A with no special casing, which is precisely why the Z-completion test in Task 2 has to run
    against the target being left rather than the target being arrived at.

    In `src/game-screen.ts`, replace the two direct selection call sites (the opening target and the
    advance inside the correct branch) with a single module-private `selectNext(mode, current)` helper.
    For Alphabet mode it returns `nextInSequence(LETTERS, current)`; for every other mode it returns
    `pickRandom(poolFor(mode), current ?? undefined)`, preserving the existing no-immediate-repeat
    behaviour for Letters and Numbers untouched. Track the current target as `string | null`, initialised
    to null, so the opening call goes through the same helper as every advance and Alphabet mode opens
    on A without a separate first-render branch.

    Nothing else in the keydown handler changes: the match check already goes through
    `acceptableCodes(currentTarget, mode)`, and `acceptableCodes` already routes Alphabet mode to the
    letter identifiers, so an Alphabet target is matched by exactly the same physical key a Letters
    target is.

    `mountGameScreen` also needs `unmountGameScreen` to clear the tracked target back to null, so
    re-entering Alphabet mode from the menu restarts at A rather than resuming mid-alphabet — the mode
    has a beginning and a parent restarting it expects that beginning.
  </action>

    particle count 120, spread 100, start velocity 35, ticks 200, gravity 1, scalar 1.1 — from three
    normalised x positions 0.2, 0.5 and 0.8 at y 0.5, scheduled at 0ms, 120ms and 240ms with
    `setTimeout`. It does not await anything and returns immediately; the target has already advanced by
    the time the first burst paints, which is exactly the instant-swap sequencing UI-SPEC locks for
    every other match. Do not introduce a second particle library, a new animation module, or new colour
