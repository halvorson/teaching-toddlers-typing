  <action>
    Add roving focus state to `src/menu.ts` (D-03, D-04). Keep a module-level `focusIndex` number and a
    module-level array of the seven created button elements, both reset by `unmountMenu()`.

    Add a module-private `focusRow(index)` that normalises the index with a modulo that tolerates a
    negative input — add the row count before taking the remainder — so Down from Quit lands on Letters
    and Up from Letters lands on Quit (UI-SPEC assumption 4). It assigns `focusIndex`, toggles the
    `focused` class so exactly one button carries it, and calls the element's `focus()` method. Driving
    both the class and native focus from this one function is what keeps the keyboard state and the
    visual state from disagreeing.

    Register a delegated `keydown` listener on the nav element, stored in a module-level variable so
    `unmountMenu()` removes exactly it. Its first statement is the auto-repeat early return, matching
    the codebase convention established in Phase 1 and recorded in 02-PATTERNS.md's Shared Patterns —
    a stuck arrow key must not spin the selection. It then switches on the event's semantic key-name
    property (the correct choice for action keys per Pitfall 4; the physical-key-code rule applies to
    gameplay character matching only): Down moves to `focusIndex + 1`, Up to `focusIndex - 1`, Home to
    0, End to the last index, and each of those four calls the event's `preventDefault` so the page
    does not also scroll. Enter and Space need no case at all — a native button already fires a click
    for both, and adding cases for them would double-fire the activation.

    Register a delegated `mouseover` listener on the nav, also stored for exact removal, that resolves
    the hovered button and calls the same `focusRow`. Routing hover through the same function is what
    gives UI-SPEC's unified "focused-or-hovered" treatment without a separate hover CSS selector that
    could disagree with the keyboard-driven class.

    At the end of `mountMenu`, call `focusRow(0)` so the Letters row is already selected on load
    (UI-SPEC assumption 3) and Up/Down/Enter work with no initial Tab press. Because plan 02-01's
    activation dispatch reads the row from the clicked button's data attribute, no activation code
    changes here.

    In `src/style.css` add the selection indicator exactly as UI-SPEC locks it (D-04): `.menu-item`
    gets `transition: color 100ms ease-out`; `.menu-item.focused` sets `color: var(--color-accent)`;
    `.menu-item.focused::after` is an empty-content block, `height: 2px`, `margin-top: 4px`,
    `background: var(--color-accent)`, `box-shadow: 0 0 8px var(--color-accent)`, with no transition of
    its own so it appears and disappears instantly with the selection rather than lagging. Give
    `.menu-item` `align-self: flex-start` and do not set a full-column width on it, so the button — and
    therefore the underline — is exactly as wide as its label, which is what UI-SPEC's "beneath the
    row's text width, not full row width" requires; the 56px minimum height from plan 02-01 keeps the
    tap target comfortable. Add `.menu-item:focus-visible { outline: none }` since the `focused` class
    is the replacement indicator and the browser's default ring would double it.
  </action>

  <action>
    Build the three-layer background entirely from CSS on existing elements — no new DOM, no new
    module, and no image asset of any kind (D-02, D-17). The base layer is the `body` background colour
    plan 02-01 already moved there; the two drifting layers are the body's `::before` and `::after`
    pseudo-elements.

    Give both pseudo-elements empty string content, `position: fixed`, `inset: 0`, `z-index: -1` and
    `pointer-events: none`, so they cover the viewport behind the transparent app container and never
    intercept a click.

    The `::before` layer carries two large soft radial gradients tinted with `--color-surface` at about
    10% opacity via `color-mix`, one biased toward the upper left and one toward the lower right, each
    fading to transparent well before the layer edge, sized at `background-size: 150% 150%` per UI-SPEC so
    the drift never exposes a layer edge. It animates `drift-a` over `40s ease-in-out
    infinite alternate`. The `::after` layer carries a single radial gradient tinted with
    `--color-accent` at about 6% — deliberately fainter, because the accent must keep reading as
    "reserved for the current selection" rather than becoming ambient chrome — and animates `drift-b`
    over `65s ease-in-out infinite alternate`. The two different durations are what produce the parallax
    read; do not give them the same duration.

    Declare both keyframe sets as a single `to` step that applies a small percentage `translate`
    transform, opposite in sign between the two layers (roughly 4%/-3% and -3%/4%). Animate only the
    transform — animating where the gradient sits or how large it is would force a full repaint on every
    frame for the entire time the menu is on screen.

    Add a `prefers-reduced-motion: reduce` block that sets `animation: none` on both pseudo-elements so
    they freeze at their starting position, matching the reduced-motion discipline Phase 1 already
    applies to the celebration. Keep it separate from the existing Phase 1 reduced-motion block or merge
    into it, either is fine, but the `animation: none` declaration must be inside a reduce block.

    Suppress the drifting layers during gameplay: when the body carries the chrome data attribute value
    `game`, set both pseudo-elements' opacity to 0, with `transition: opacity 100ms ease-out` on the
    layers so the change rides the same ~100ms feel as every other transition in the app (D-07, D-18).
    A mode screen must stay the plain dark field Phase 1 established; the windowed screens plan 02-04
    adds keep the value `menu` and therefore keep the background.

    Finally add the menu's entrance crossfade (D-07, D-18): a `screen-fade-in` keyframe set going from
    opacity 0 to 1, applied to the `.menu` nav at `100ms ease-out`. The game screen already crossfades
    through the target element's existing opacity transition, so it needs nothing further.
  </action>
