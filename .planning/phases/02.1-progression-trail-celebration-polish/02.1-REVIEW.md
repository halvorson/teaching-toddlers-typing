## Warnings

### WR-02-RESIDUAL: `.focused` class resync only survives the manual-copy textbox's first blur

**File:** `src/menu.ts:175` (also relevant: `src/menu.ts:167`, `src/menu.ts:338-345`)

**Issue:** `renderManualFallback()` attaches the resync listener as one-shot:

```ts
urlBox.addEventListener('blur', () => syncFocusedClass(), { once: true })
```

This correctly resyncs `.focused` the *first* time focus leaves the manual-copy `urlBox` (e.g., Tab forward to the next button). But `{ once: true }` means the listener is gone after that first firing. The delegated `handleFocusIn` on `nav` (line 338) explicitly ignores `urlBox` because it only matches `button[data-row]` elements — so if the user later Tabs (or Shift+Tabs) *back* into `urlBox` a second time while the fallback panel is still showing, and then Tabs back out again, nothing resyncs `.focused` on that second exit. The indicator can be left highlighting a stale button while real keyboard focus has moved elsewhere, until some other interaction (arrow key, hover, or landing focus on a *different* tracked button) happens to correct it.

Reproduction path:
1. Activate Share (clipboard write fails in this browser/context) → manual fallback renders, `urlBox` focused, `.focused` cleared from all buttons.
2. Tab forward → `blur` fires once, resyncs `.focused` onto the current `focusIndex`'s button, consuming the one-shot listener.
3. Shift+Tab back into `urlBox` → `handleFocusIn` ignores it (not a `button[data-row]`); `.focused` stays wherever step 2 left it, now visually wrong (real focus is in `urlBox`).
4. Tab forward again → no `blur` listener remains on `urlBox` (already consumed in step 2) → `.focused` does not get a fresh, guaranteed-correct resync on this exit; correctness now depends on whichever button focus happens to land on matching the stale `focusIndex` by coincidence.

Impact is cosmetic only (no functional break, no data loss) and self-heals on most subsequent interactions, but it violates the invariant the module's own header comment and this fix's inline comments promise ("the keyboard state, the mouse state and the visual `focused` class can never disagree").

**Fix:** Don't use `{ once: true }`. Either keep the listener attached for the lifetime of `urlBox` (it is naturally cleaned up when `resetShareFeedback()`/`unmountMenu()` removes `shareFallbackEl` from the DOM and drops the module's last reference to it), or better, extend the delegated `nav` listener set with a `focusout` handler that specifically resyncs when `event.target === urlBox`:

```ts
// in renderManualFallback(), replace the once-listener with a persistent one:
urlBox.addEventListener('blur', () => syncFocusedClass())
```

Since `urlBox` itself is discarded (and its listeners GC'd) every time `resetShareFeedback()` runs or the menu unmounts, a persistent (non-`once`) listener carries no leak risk here and correctly resyncs on every exit, not just the first.

## Info

### IN-01: Rapid double-activation of Share can orphan a "Copied!" revert timer

**File:** `src/menu.ts:185-197` (`runShare`), `src/menu.ts:115-124` (`showCopiedFeedback`)

**Issue:** Pre-existing (not introduced by WR-01's fix, and not fully addressed by it): `mountGeneration` only distinguishes *different mounts*, not *overlapping activations within the same mount*. If a parent double-activates the Share row before the first `runShare()` promise resolves, two independent copy chains run concurrently. If both eventually resolve to `showCopiedFeedback()`, the second call overwrites `copiedTimeoutId` with a new timer id without clearing the first one — the first timer is never cancelled and still fires later, redundantly resetting the label back to `MENU_LABELS.share` (possibly while the second timer is also about to do the same, or has already reset a further state change). Worst case is a brief incorrect/flickering label; no data loss or crash.

**Fix:** Not required for this phase, but worth a follow-up: disable/ignore the Share row's activation while `runShare()` is in flight (e.g., a module-level `shareInFlight` boolean checked in `handleClick`'s `'share'` branch), or clear the existing `copiedTimeoutId` before scheduling the new one inside `showCopiedFeedback()` (it already does this pattern correctly in `resetShareFeedback()`, just not inside `showCopiedFeedback()` itself).
