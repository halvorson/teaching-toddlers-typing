# Phase 02.1: Code Review Report

**Reviewed:** 2026-08-13T00:00:00Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Reviewed the star-trail (`trail.ts`), celebration-scaling (`celebrate.ts`), settings persistence
(`settings-store.ts`, `settings.ts`), and the modules they wire into (`game-screen.ts`, `main.ts`,
`menu.ts`, `router.ts`, `style.css`). Cross-checked behavior against `02.1-CONTEXT.md` and the
phase plans/summaries (trail reset-on-mode-entry, viewport-scale clamp range, toggle-gated
incorrect-key wipe) — the implementation matches the locked decisions on all of those points, and
no crash, security, or data-loss defect was found.

The issues found are all robustness/consistency gaps, concentrated in two places: `menu.ts`'s
Share-row async flow (a stale copy-result can land on a since-remounted menu, and the manual
fallback silently breaks the module's own "focus state and the `.focused` class can never
disagree" invariant), and an inconsistency in `celebrate.ts` where the new
`celebrateAlphabetComplete()` is carefully made cancelable on quit but the older `celebrate()`
burst is not. `settings-store.ts` also hands back a shared mutable default object by reference,
which is fine today but fragile for future callers.

## Warnings

### WR-01: Stale Share-copy result can apply its "Copied!"/fallback UI to a since-remounted menu

**File:** `src/menu.ts:152-159` (`runShare`), interacting with the module-level refs at
`src/menu.ts:48-50` and the guards in `showCopiedFeedback` (`src/menu.ts:97-106`) and
`renderManualFallback` (`src/menu.ts:116-143`)

**Issue:** `shareLabelEl`/`shareButtonEl` are module-level variables reassigned on every
`mountMenu()` call. `runShare()` is fire-and-forget (`void runShare()` in `handleClick`,
`src/menu.ts:251`) and its `await shareCurrentUrl()` can take an arbitrary amount of time — most
notably if the browser shows a clipboard-permission prompt, which can stay pending for seconds. If
the player navigates away from the menu (e.g. launches a game mode) and back again before that
promise resolves, `mountMenu()` runs again and reassigns `shareLabelEl`/`shareButtonEl` to the
*new* mount's elements. When the stale promise finally resolves, `showCopiedFeedback()` or
`renderManualFallback()` still passes their `!shareLabelEl` / `!shareButtonEl` null-guards (the
refs are non-null, just pointing at the new mount) and mutates the new mount's Share row even
though the current session never clicked Share. This doesn't crash anything, but it silently
contradicts the module's own click that supposedly caused it, and could show a misleading
"Copied!" state on a menu visit where nothing was copied.

**Fix:** Give each `mountMenu()` call a generation token and have `runShare()` bail out if the
token has changed by the time the promise resolves, e.g.:

```typescript
let mountGeneration = 0

export function mountMenu(container: HTMLElement, handlers: MenuHandlers): void {
  const myGeneration = ++mountGeneration
  // ...
  async function runShare(): Promise<void> {
    const result = await shareCurrentUrl()
    if (myGeneration !== mountGeneration) return // menu was remounted while we awaited
    if (result !== 'manual-required') {
      showCopiedFeedback()
      return
    }
    renderManualFallback()
  }
  // ...
}

export function unmountMenu(): void {
  mountGeneration++ // invalidate any in-flight runShare() from this mount
  // ...
}
```

### WR-02: Manual share fallback moves keyboard focus without going through `focusRow()`, breaking the documented focus-sync invariant

**File:** `src/menu.ts:142` (`urlBox.select()`) vs. the module's own contract at
`src/menu.ts:57-65` ("...driven through the single `focusRow` function so the keyboard state, the
mouse state and the visual `focused` class can never disagree")

**Issue:** `renderManualFallback()` calls `urlBox.select()`, which moves real DOM focus onto the
inserted `<input>`. That input is not a `button[data-row]` element, so `handleFocusIn`
(`src/menu.ts:299-306`) — the delegated listener whose entire purpose is keeping the `.focused`
class in sync with real focus — ignores it (`target.closest('button[data-row]')` returns `null`
and the handler returns early). The result: DOM focus is on the URL textbox, but the `.focused`
class visually stays on the Share button (`focusIndex` unchanged), directly contradicting the
"can never disagree" invariant the module's own top-of-file comment asserts. A subsequent
Tab/Shift+Tab press from the textbox can also land keyboard focus somewhere the `.focused`
indicator never reflects.

**Fix:** Either bring the fallback input into the roving-focus system (least invasive: explicitly
clear the `.focused` class from all menu buttons when focus leaves them for the fallback box), or
document this as an intentional, narrow exception and add a `blur`/`focusout` handler on `urlBox`
that calls `focusRow(focusIndex)` again to resync when the user tabs away from it.

### WR-03: `celebrate()`'s in-flight burst isn't cancelable on quit, unlike `celebrateAlphabetComplete()`

**File:** `src/celebrate.ts:70-83` vs. `src/celebrate.ts:98-115`; consumed at
`src/game-screen.ts:84` (`void celebrate(...)`) and cancelled only for the Z-completion path at
`src/game-screen.ts:112-129` (`unmountGameScreen`'s `pendingCelebrationTimers.forEach(clearTimeout)`)

**Issue:** `celebrateAlphabetComplete()` was deliberately built to return its `setTimeout` ids so a
caller that quits mid-celebration can cancel bursts that haven't fired yet ("so a burst can never
fire on a screen the player has already left" — `src/celebrate.ts:93-96`). The ordinary
`celebrate()` burst gets no equivalent treatment: it's invoked as `void celebrate(...)` with no
handle returned, and its first call in a session pays for a dynamic `import()` that resolves
asynchronously. If the player matches a key and immediately presses Escape (or the fullscreen
exit path fires `quitToMenu()`) before that import settles, `unmountGameScreen()` has no way to
suppress the pending `fireBurst()` call, and a confetti burst can fire after the game screen has
already been torn down and the menu is showing. The race window is small (the import is cached
after the first celebration in a session), but it's the exact class of bug the codebase already
recognized and fixed for the Z-completion path — leaving the ordinary path unprotected is an
inconsistency worth closing.

**Fix:** Have `celebrate()` (via `fireBurst`) accept/return a cancellation handle the same way
`celebrateAlphabetComplete()` does, and have `unmountGameScreen()` cancel it alongside
`pendingCelebrationTimers`. A minimal version: track the in-flight promise/AbortController at
module scope in `celebrate.ts` and expose a `cancelPendingCelebration()` export that
`unmountGameScreen()` calls.

### WR-04: `readSettings()` returns the shared `DEFAULT_SETTINGS` object by reference

**File:** `src/settings-store.ts:19, 30, 35, 40`

**Issue:** `DEFAULT_SETTINGS` is a single module-level object literal. Every fallback path in
`readSettings()` (`!raw`, failed shape check, caught exception) returns that exact same object
reference rather than a copy. No current caller mutates the returned value
(`game-screen.ts:98`, `settings.ts:50` both only read `.resetTrailOnMistake`), so there's no live
bug today — but this interface is explicitly documented as the shape Phase 3's sound toggle and
Phase 4's stats preference will extend (`settings-store.ts:1-9`), and any future caller that does
`const s = readSettings(); s.someField = x` would silently corrupt the app-wide default for the
rest of the session (every subsequent "missing/corrupt localStorage" read would return the
mutated object).

**Fix:** Return a fresh copy at each fallback site, e.g. `return { ...DEFAULT_SETTINGS }`, or
`Object.freeze(DEFAULT_SETTINGS)` so an accidental mutation throws immediately in strict mode
instead of silently succeeding.

## Info

### IN-01: Share row's "Copied!" state change isn't announced to assistive tech

**File:** `src/menu.ts:97-106` (`showCopiedFeedback`)

**Issue:** Swapping the Share button's visible label to "Copied!" changes its accessible name
(the label `<span>` is the button's only non-`aria-hidden` content), but nothing marks this region
as an `aria-live` region, so a screen-reader user gets no announcement that the copy succeeded.

**Fix:** Add `aria-live="polite"` (or a visually-hidden live region referenced by the button) so
the confirmation is announced, not just visually shown.

### IN-02: Duplicated `prefers-reduced-motion` media query blocks in `style.css`

**File:** `src/style.css:51-56, 270-286, 288-294`

**Issue:** Three separate `@media (prefers-reduced-motion: reduce) { ... }` blocks exist for
different selectors (drifting background, `#target.correct-pulse`, `.star-trail__star`). This is
functionally correct but is unnecessary duplication that increases the chance a future edit
updates one block and forgets the others.

**Fix:** Consolidate into a single `@media (prefers-reduced-motion: reduce) { ... }` block
containing all three rule sets, or group them under a clear comment banner if kept separate for
readability.
