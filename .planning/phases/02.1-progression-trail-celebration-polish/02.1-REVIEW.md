## Summary

This is the final re-review verifying the fix for WR-02-RESIDUAL, the last outstanding Warning
from iteration 2: the `.focused` class resync `blur` listener on the Share row's manual-copy
`urlBox` was registered with `{ once: true }`, so it only resynced the indicator on the *first*
blur of the textbox, leaving it capable of drifting from real focus on a second or later
Tab-in/Tab-out cycle while the manual-fallback panel was still visible.

**Verified against commit `765e913`** (`git show 765e913 -- src/menu.ts`): the change is a clean,
minimal diff — only the `blur` listener registration at what is now `src/menu.ts:180` and its
surrounding comment block changed. `{ once: true }` was removed:

```ts
urlBox.addEventListener('blur', () => syncFocusedClass())
```

**Correctness check — confirmed correct and complete:**

- Every call to `renderManualFallback()` creates a brand-new `urlBox` element and attaches a
  fresh `blur` listener to it (`src/menu.ts:134-181`). There is no risk of listener
  accumulation across repeated Share activations, since the prior `urlBox` (and its listener) is
  always fully discarded first: `resetShareFeedback()` (`src/menu.ts:96-108`, called
  synchronously at the top of the Share click handler, `src/menu.ts:294`) removes the previous
  `shareFallbackEl` from the DOM and nulls the module reference before a new one can be created.
  `unmountMenu()` does the same on teardown (`src/menu.ts:392-395`). Since the old `urlBox` has no
  other references once detached and nulled, the node — and the listener closure attached to it,
  which only captures the module-level `syncFocusedClass` function, not `urlBox` itself — is
  eligible for garbage collection. The "persistent listener carries no leak risk" rationale in the
  updated comment holds.
- Traced the full reproduction path from the WR-02-RESIDUAL finding (Tab forward, Shift+Tab back
  into `urlBox`, Tab forward again) against the fixed code: because the `blur` listener is no
  longer one-shot, `syncFocusedClass()` now fires on *every* exit from `urlBox`, not just the
  first, closing the exact gap described (previously, a second blur cycle had no listener left to
  correct a stale `.focused` class, since `handleFocusIn`, `src/menu.ts:343-350`, ignores non-
  `button[data-row]` elements like `urlBox`).
- Checked the DOM-removal interaction: when `resetShareFeedback()`/`unmountMenu()` removes
  `shareFallbackEl` while `urlBox` still holds focus, node removal synchronously fires the `blur`
  event per spec. The persistent listener then runs `syncFocusedClass()` against whatever
  `menuButtons`/`focusIndex` state is current at that moment — in `unmountMenu()` this can occur
  either before or after `menuButtons` is reset to `[]` depending on call order, but `Array.forEach`
  on an empty array is a harmless no-op either way, and `classList.toggle` on now-detached button
  nodes throws no error. This ordering pre-dates the `{ once: true }` fix and is unaffected by it.
- `tsc --noEmit` passes clean; no compile-time regressions.

**No new issues were introduced by this fix.** The diff touches only the listener registration and

## Info

### IN-01: Rapid double-activation of Share can orphan a "Copied!" revert timer

**File:** `src/menu.ts:190-202` (`runShare`), `src/menu.ts:115-124` (`showCopiedFeedback`)

**Issue:** Pre-existing, carried forward from iteration 3 (not in scope for this iteration's fix
and not a regression introduced by it). `mountGeneration` distinguishes *different mounts* but not
*overlapping activations within the same mount*. If the Share row is activated twice before the
first `runShare()` promise resolves, two independent copy chains run concurrently. If both resolve
to `showCopiedFeedback()`, the second call overwrites `copiedTimeoutId` with a new timer id without
clearing the first, so the first timer is never cancelled and still fires later, redundantly
resetting the label. Worst case is a brief incorrect/flickering label; no data loss or crash.

**Fix:** Not required for this phase. A follow-up could disable/ignore the Share row's activation
while `runShare()` is in flight, or have `showCopiedFeedback()` clear any existing
`copiedTimeoutId` before scheduling a new one — mirroring the pattern `resetShareFeedback()`
already uses.
