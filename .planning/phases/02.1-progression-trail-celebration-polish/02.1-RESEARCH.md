## User Constraints (from CONTEXT.md)

### Locked Decisions

**Trail Visual & Distribution**
- Stars are randomly scattered across the whole background — not a linear progress bar or
  high-score-style ribbon. The intended effect: the background subtly gets "more cluttered" as
  the correct-match streak continues, purely ambient and decorative.
- Star shape: small glowing CSS-only dot (~6px radial-gradient circle) using the existing accent
  palette — no image assets, no reuse of canvas-confetti (that's reserved for the burst
  celebration, keeping the trail visually distinct from it).
- No engineered cap on star count — effectively unbounded for a normal session. User's mental
  ceiling is ~1000 stars, but no code needs to enforce that; don't build cap/cycling logic.
- Trail resets when switching modes (Letters → Numbers → Alphabet) — each mode starts with an
  empty trail. Within a single mode, the trail persists and accumulates across all rounds played
  in that mode this session (this is the "persists across the play session" behavior from the
  ROADMAP, scoped per-mode rather than app-wide).

**Trail Reset Toggle & Settings Screen**
- Build a minimal Settings screen now: a windowed (non-fullscreen) screen reusing Phase 2's
  existing windowed-screen visual pattern (dark pearlescent, simple layout), with exactly one row:
  "Reset trail on mistake" toggle, default OFF. Phase 3 (Sound & Audio Settings) will extend this
  same screen with the sound toggle later — this phase does not duplicate that screen.
- When the toggle is ON, an incorrect key press triggers a full trail wipe (the scattered trail
  clears completely and restarts empty) — not a partial decay/fade.
- When the toggle is OFF (default), incorrect key presses have no effect on the trail at all —
  only the mode-switch reset (above) and the toggle-gated incorrect-key reset ever clear it.

**Celebration Scaling**
- Confetti bursts (both the ordinary per-match celebration and the bigger Alphabet Z-completion
  celebration) scale via a proportional factor computed from current viewport size against a
  1280x800 baseline, clamped to a 0.8x–2.5x range so extreme window sizes never produce a broken
  or absurdly oversized/tiny burst.
- "Travels further" is implemented by scaling `startVelocity` up with the viewport factor while
  keeping gravity/decay/ticks in the same ratio as today's tuning — this increases travel distance
  without changing the perceived deceleration curve, so it doesn't read as "sped up," matching the
  ROADMAP's "at the same animation speed" requirement.
- Both `celebrate()` and `celebrateAlphabetComplete()` apply the same viewport-scale multiplier on
  top of their existing distinct base tunings (40/60 vs. 120/100 particleCount/spread etc.),
  consistent with the shared `fireBurst()` helper both already funnel through.

**Trail Placement & Layering**
- Trail renders on a dedicated fixed full-viewport layer, positioned below all interactive/text UI
  (target letter, menu text) and above the existing drifting menu background — never obscures
  gameplay or legibility.
- Trail is visible only during gameplay (Letters/Numbers/Alphabet modes) — hidden on the home menu,
  reusing the existing `data-chrome="game"` suppression pattern already established for the
  drifting background in Phase 2.
- Under `prefers-reduced-motion`, new stars appear instantly with no pop-in/fade transition —
  consistent with the reduced-motion handling already established in `celebrate.ts` and the menu
  background.

### Claude's Discretion
- Exact DOM/rendering approach for the trail layer (absolutely-positioned divs vs. a single canvas)
  as long as it stays CSS-driven/cheap and matches the above visual description, using
  CSS-relative units (rem/vw) for star sizing/positioning so it scales naturally with viewport.
- Exact random-distribution algorithm for star placement (e.g. simple `Math.random()` x/y within
  safe margins) as long as it reads as scattered, not patterned.
- Precise glow/gradient values for the star dot, within the existing accent palette.

### Deferred Ideas (OUT OF SCOPE)
- Enforcing a hard cap (e.g. 1000 stars) with cycling/eviction logic — explicitly not needed per
  user ("I don't think we need to program that").
- The full Statistics screen and any other Settings toggles beyond the trail-reset one — those
  belong to Phase 3 (sound toggle) and Phase 4 (stats display) respectively.

**Note:** `02.1-UI-SPEC.md` (approved 2026-08-14, checker sign-off 6/6) already resolves nearly
every implementation-level gap CONTEXT.md left to discretion — exact CSS, exact formula, exact
markup. This research treats UI-SPEC's concrete values as ground truth and focuses on verifying
them against the *actual* current codebase state (see Pitfall 1 below — this matters more than
usual for this phase).

## Summary

This phase is a **narrow, well-specified polish pass** on an existing, small vanilla-TypeScript
codebase (9 files, no framework, no test suite). `02.1-UI-SPEC.md` already pins every visual
value (star CSS, toggle CSS, viewport-scale formula) with checker sign-off — the planner's job is
almost entirely to sequence concrete, already-specified edits into existing files, plus one
genuinely new file (a Settings-screen module) and one genuinely new persistence mechanism
(localStorage, used nowhere in this codebase today).

**The single most important research finding**: `02.1-UI-SPEC.md` and CONTEXT.md both describe
the Settings screen as "reusing Phase 2's windowed-panel pattern" as if that pattern already
exists in code. It does not. Phase 2 (all 4 plans, confirmed complete via SUMMARY files and git
log) shipped the menu, game modes, fullscreen, and share affordance — but `menu.ts:252`'s comment
still reads "stats and settings stay undispatched — their real content belongs to" future phases,
and a direct read of every file in `src/` confirms: no `settings.ts`/`panels.ts` module exists, no
`.windowed-panel`/`.panel-back` CSS class exists in `style.css`, the `Screen` union in `router.ts`
has no `'settings'` member, and `main.ts`'s `mountScreen` switch has no case for it. The
"windowed-panel pattern" was *speculatively designed* in `02-UI-SPEC.md` and `02-PATTERNS.md`
during Phase 2 planning but never implemented — Phase 2's actual plans (02-01 through 02-04)
scoped down to leave Settings/Statistics as bare undispatched menu rows. Phase 2.1 is therefore
the **first phase to write any of this code**, not a phase that extends existing panel code. The
planner must treat `02.1-UI-SPEC.md`'s concrete CSS/markup values as the spec to build from
scratch, not values to "reuse verbatim" from an existing implementation.

Everything else is comparatively low-risk: canvas-confetti's `startVelocity` scaling is a pure
math-and-one-line change inside the existing single `fireBurst()` chokepoint; the star trail is a
straightforward DOM-append pattern matching the codebase's existing render/reflow conventions; and
localStorage read/write is a small, well-trodden try/catch pattern with no library needed.

**Primary recommendation:** Implement in three independent-ish slices — (1) router+main.ts+new
`settings.ts` module to make the Settings screen reachable and functional with its toggle and
localStorage persistence, (2) a new `trail.ts` module (or equivalent) wired into
`game-screen.ts`'s existing correct/incorrect handlers and `mountGameScreen`/`unmountGameScreen`
lifecycle, (3) a small, isolated diff to `celebrate.ts`'s `fireBurst()` adding
`viewportScaleFactor()`. Slices 2 and 3 touch disjoint files from slice 1 and from each other,
so they parallelize cleanly; slice 2 needs slice 1's toggle value only for the incorrect-keypress
branch (a simple read call, not a structural dependency).

**Why a separate `trail.ts` and a separate settings-persistence module:** `game-screen.ts`'s
incorrect-keypress branch (line 90-94 today) needs to know the toggle's current value to decide
whether to wipe the trail — but it should not need to import DOM-mounting logic for the Settings

function) from "render the Settings screen" (DOM mounting) avoids a circular-feeling dependency
and matches the codebase's existing separation (`clipboard.ts`'s `currentShareUrl()` is read by
both `menu.ts` and its own internal fallback panel, for the same reason).

### Pattern 1: Trail star-add funneled through the existing correct-match branch

**What:** One star-append call added directly inside `game-screen.ts`'s existing `if
(currentTarget !== null && acceptableCodes(...))` branch (verified at `game-screen.ts:72-89`),
alongside the existing `celebrate()`/`celebrateAlphabetComplete()` call — not a second keydown
listener.

**When to use:** Any time a new "also happens on correct match" behavior is added — this project's
established pattern (confirmed by how `celebrate()`, `renderTarget()`, and the `correct-pulse`
class-restart all already live in this single branch) is to extend the one branch, never add a
second listener that re-derives the match condition.

### Pattern 2: Trail clear-on-mode-entry via `mountGameScreen`'s existing idempotent unmount

**What:** `mountGameScreen()` (verified `game-screen.ts:51-99`) already calls
`unmountGameScreen()` defensively at its own top (line 52) before every mount — this is the
existing "start clean" hook. The trail's "cleared every time `mountGameScreen()` runs" requirement
(UI-SPEC's Lifecycle section) should call the trail-layer's clear/reset function from inside this
same mount function, not from a separate mode-switch-detection mechanism.

**When to use:** Any per-mode-entry reset. This mirrors how `currentTarget = null` is already
reset in `unmountGameScreen()` (line 116) — the trail's per-mode state should follow the same
reset-on-unmount-then-repopulate-on-mount shape.

### Pattern 3: `viewportScaleFactor()` as a pure function inside `celebrate.ts`, called once per `fireBurst()` invocation

**What:** A new, pure, side-effect-free function co-located in `celebrate.ts` (not a new module —
UI-SPEC assumption 7 is explicit this lives inside `fireBurst()` itself), called fresh on every
burst with no caching and no resize listener.

**When to use:** Exactly once, at the single `fireBurst()` chokepoint both `celebrate()` and
`celebrateAlphabetComplete()` already funnel through (verified `celebrate.ts:31-40` — this is the
*only* place `confetti(...)` is invoked in the entire codebase).

**Example (grounded in the actual current file, `celebrate.ts:31-40`):**
```typescript
// src/celebrate.ts — current code (read this session, lines 31-40)
async function fireBurst(opts: BurstOptions): Promise<void> {
  if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) return

  try {
    const { default: confetti } = await import('canvas-confetti')
    confetti({ ...opts, colors: CONFETTI_COLORS })
  } catch {
    // Confetti is decorative — swallow load failures so the core game keeps working.
  }
}

// NEW this phase — per 02.1-UI-SPEC.md's Celebration Scaling Contract:
function viewportScaleFactor(): number {
  const widthRatio = window.innerWidth / 1280
  const heightRatio = window.innerHeight / 800
  const factor = Math.sqrt(widthRatio * heightRatio)
  return Math.min(2.5, Math.max(0.8, factor))
}

// fireBurst's confetti(...) call becomes:
//   confetti({ ...opts, startVelocity: opts.startVelocity * viewportScaleFactor(), colors: CONFETTI_COLORS })
```
Both `celebrate()` (base `startVelocity: 25`, verified `celebrate.ts:50`) and
`celebrateAlphabetComplete()` (base `startVelocity: 35`, verified `celebrate.ts:83`) are
**unchanged** by this — they still pass their existing literal values; only `fireBurst()`'s
internals change.

### Anti-Patterns to Avoid

- **A second `keydown` listener for the trail.** `game-screen.ts` already registers exactly one
  document-level `keydown` listener per mount (verified: `document.addEventListener('keydown',
  handler)` appears exactly once, `game-screen.ts:98`). Adding a second listener for trail logic
  would double-process every keypress and risk the two listeners disagreeing about what counts as
  "correct" if the match logic ever changes in only one place.
- **Caching `viewportScaleFactor()`'s result or adding a `resize` listener.** UI-SPEC explicitly
  rejects this ("Computed fresh on every burst... no resize listener needed — fullscreen
  transitions are naturally picked up at fire-time"). A cached/listened value adds state and a
  cleanup obligation (listener removal on unmount) for no benefit — `window.innerWidth/innerHeight`
  reads are cheap and the burst is momentary.
- **Treating "reuse Phase 2's windowed-panel pattern" as literal code reuse.** See Pitfall 1 below
  — there is no existing panel code to import from. The planner must generate real new markup/CSS
  from `02.1-UI-SPEC.md`'s Settings Screen & Toggle Contract, not search the codebase for a
  `panels.ts` or `.windowed-panel` class that doesn't exist.
- **Storing the toggle value in a module-level variable only (no localStorage read on boot).**
  TRAIL-02 requires the setting to control behavior across the *session*, and `02.1-UI-SPEC.md`'s
  Persistence section requires a versioned localStorage key — an in-memory-only variable would
  reset to the default every page load, defeating the point of a persisted setting (though the
  *fallback* for unavailable localStorage is correctly in-memory-only per assumption 6).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Confetti physics (gravity/decay/particle rendering) | A custom canvas particle system | The existing `canvas-confetti` dependency, already installed and already the single source of all burst rendering in this codebase | Already solved, already tuned, already the only particle-physics code in the project (`celebrate.ts`'s comment: "no second animation library, no second particle system") — this phase only adjusts one numeric input, never reaches for a new engine |
| localStorage read/write robustness (try/catch, JSON parse failure, quota errors, private-browsing unavailability) | A generic ad-hoc `localStorage.getItem`/`setItem` call with no guard | A small dedicated read/write pair wrapped in try/catch, matching `02.1-UI-SPEC.md`'s explicit "silent in-memory-only fallback" contract | `localStorage.setItem` throws in Safari private browsing and can throw `QuotaExceededError`; `JSON.parse` throws on malformed/hand-edited data. A single well-tested small wrapper (a handful of lines) avoids scattering try/catch across every read/write site — and this project has zero precedent for localStorage yet, so getting the *one* wrapper right matters for Phase 3/4's later reuse of the same schema pattern |
| Accessible toggle-switch keyboard/ARIA behavior | A custom keydown handler re-implementing Enter/Space activation | A native `<button role="switch" aria-checked>` (UI-SPEC's locked choice) | Native `<button>` already fires `click` on both Enter and Space with zero extra JS — reinventing this with a `<div>` + manual keydown handling is both more code and more likely to miss an edge case (double-firing, missing Space support) than the browser's built-in behavior |
| Random scattered placement | A jittered-grid or Poisson-disc sampling algorithm | Plain `Math.random()` per axis, per star (UI-SPEC's locked formula) | CONTEXT.md explicitly scopes this to "as long as it reads as scattered, not patterned" — Poisson-disc/rejection-sampling is a real technique for avoiding visual clustering, but is unnecessary complexity for a decorative ambient effect with no functional requirement to avoid overlap |

**Key insight:** This phase's entire scope is additive polish on a codebase that already solved
the hard problems (fullscreen, physical-key matching, confetti physics, clipboard fallback
chains) in Phase 1/2. The temptation to hand-roll would show up as: writing a second particle
engine (don't — one line of math into the existing one), writing a bespoke settings-persistence
abstraction bigger than the ~10-line pattern this phase needs (don't — Phase 4 will need the same
small pattern again, keep it minimal and copyable), or over-engineering the star placement
algorithm for a purely decorative, no-collision-consequence element (don't — `Math.random()` is
sufficient and explicitly sanctioned).

## Common Pitfalls

### Pitfall 1: Treating "Phase 2's windowed-panel pattern" as already-implemented code

**What goes wrong:** A planner or executor searches the codebase for an existing `panels.ts`,
`.windowed-panel` CSS class, or `settings` Screen-union member expecting to extend it, finds
nothing, and either (a) wastes time confused about where the "existing" pattern lives, or (b)
silently invents a different structure than what `02.1-UI-SPEC.md` specifies, drifting from the
approved design.

**Why it happens:** Both `02.1-CONTEXT.md` ("reusing Phase 2's existing windowed-screen visual
pattern") and `02.1-UI-SPEC.md` ("reuses Phase 2's windowed-panel pattern verbatim") describe the
pattern as if it's an established, already-built thing to extend. It was *designed* during Phase 2
planning (`02-UI-SPEC.md`'s Windowed panels section, `02-PATTERNS.md`'s speculative
`src/panels.ts`/`.windowed-panel` code) but Phase 2's actual four plans (verified via all four
`02-0N-SUMMARY.md` files, all `status: complete`) never implemented it — they scoped down to
"stats and settings stay undispatched" (verbatim comment, `menu.ts:252`, confirmed present in the
current file).

**How to avoid:** The planner should generate tasks that create this pattern for the first time,
using `02.1-UI-SPEC.md`'s "Settings Screen & Toggle Contract" section as the literal spec (it
already has the exact CSS: `max-width: 480px`, `border-radius: 12px`, `padding: 32px`,
`background: var(--color-surface)`, the toggle markup/CSS, etc.) — treat that section as "build
this," not "these values already exist somewhere, go find them."

**Warning signs:** Any task action that says "extend the existing Settings panel" or "reuse
`panels.ts`" without first creating those files/classes is a signal this pitfall has been hit.

### Pitfall 2: `#star-trail`'s z-index depends on a coordinated change to `body::before`/`body::after`

**What goes wrong:** If the new `#star-trail` layer is simply given `z-index: -1` without also
moving the *existing* drifting-background pseudo-elements from `z-index: -1` down to `-2`, the
trail and the drifting background will occupy the same stacking layer and their paint order
becomes DOM-order-dependent/unpredictable, risking the trail being visually buried under (or
fighting with) the drifting background instead of sitting cleanly between it and the UI.

**Why it happens:** `style.css`'s current `body::before`/`body::after` rule (verified lines 16-24)
sets `z-index: -1` today. `02.1-UI-SPEC.md`'s Star Trail Contract explicitly calls this out
("bump the existing... layers... down to `z-index: -2`... no other z-index in the codebase needs
to change") — it's a coordinated two-part CSS edit, not just an additive one.

**How to avoid:** The task/verify step for the trail-layer CSS must include the `body::before,
body::after { z-index: -2; }` change as part of the same diff, and a verify grep confirming both
values landed (e.g. grep for `z-index: -2` on the pseudo-elements and `z-index: -1` on
`#star-trail`).

**Warning signs:** A star-trail layer that "sometimes" appears behind the drifting background
depending on which stylesheet rule wins is a symptom.

### Pitfall 3: `Screen` union / `VALID_SCREENS` / `mountScreen` switch / `menu.ts` dispatch are four separate edit sites that must all agree

**What goes wrong:** Adding a `'settings'` screen requires coordinated edits across four different
files/locations — missing any one produces either a TypeScript error (switch not exhaustive,
`noFallthroughCasesInSwitch` is enabled per `tsconfig.json`) or a silent no-op (menu row click
does nothing because `handleClick` in `menu.ts` still has no dispatch branch for `'settings'`).

**Verified current state of each site (read this session):**
1. `router.ts:8` — `export type Screen = 'menu' | 'letters' | 'numbers' | 'alphabet'` (no
   `'settings'`)
2. `router.ts:10` — `const VALID_SCREENS: readonly Screen[] = Object.freeze(['menu', 'letters',
   'numbers', 'alphabet'])` (no `'settings'`)
3. `main.ts:24-50` — `mountScreen()`'s two switch statements (unmount-by-`currentScreen`,
   mount-by-`screen`) both only branch on `'menu'` and the three game modes; no `'settings'` case
   in either
4. `menu.ts:238-254` — `handleClick`'s dispatch only handles `isGameplayRow(row)` and `row ===
   'quit'`/`'share'`; the trailing comment confirms `settings` is deliberately undispatched today

**How to avoid:** Treat these four sites as one atomic change-set in the plan — a single task (or
tightly sequenced tasks within one wave) that updates all four together, with a verify step
grepping for `'settings'` in each of the four locations.

**Warning signs:** `npm run build` failing on a non-exhaustive switch (TS2678/7027-class errors)
after only `router.ts` is touched; or a build that succeeds but clicking the Settings menu row
visibly does nothing.

### Pitfall 4: `startVelocity` scaling interacting with `celebrateAlphabetComplete()`'s `setTimeout`-scheduled bursts

**What goes wrong:** `celebrateAlphabetComplete()` (verified `celebrate.ts:74-91`) schedules three
*separate* `fireBurst()` calls via `window.setTimeout` at 0/120/240ms — if a resize or fullscreen
transition happens to land in that ~240ms window, each burst could compute a different
`viewportScaleFactor()`, producing three visually-inconsistent burst sizes in one Z-completion
celebration.

**Why it happens:** `viewportScaleFactor()` is deliberately uncached/unlistened per UI-SPEC — this
is an accepted, explicitly-reasoned tradeoff ("negligible drift risk given the ~240ms total window
and no resize event realistically landing mid-sequence"), not an oversight. Documenting it here so
the planner doesn't "fix" it by adding a cache that would then violate the "compute fresh, no
resize listener" contract, or file it as an unexpected bug during manual QA.

**How to avoid:** No code change needed — this is a known, accepted, low-probability edge case.
If manual QA does observe visibly mismatched burst sizes across the three staggered bursts (would
require a literal window resize mid-celebration), that is expected behavior per the approved
contract, not a defect.

### Pitfall 5: Unbounded DOM node growth has no automated performance gate

**What goes wrong:** With no engineered cap (explicit user decision), a very long single-mode play
session accumulates one DOM node per correct match indefinitely. There is no automated way to
catch a real-world performance cliff (e.g. if a session runs to several thousand correct matches)
because this project has no test suite (per CLAUDE.md) and no performance budget was specified.

**Why it happens:** This is an explicitly *accepted* tradeoff, not a bug — `02.1-UI-SPEC.md`'s UI
Considerations table marks this "overflow" case as `🧪 backstop`: "verified only by manual QA."

**How to avoid:** No code fix is in scope. The planner should ensure the phase's manual-QA/UAT
checklist includes at least one extended-session smoke check (e.g. "play 100+ rounds in one mode,
confirm the app still feels responsive") so this known gap gets at least one manual look before
shipping, consistent with how Phase 2's `02-VALIDATION.md` handled its own manual-only items.

**Warning signs:** None automatable — this is inherently a manual-QA-only concern per the approved
design.

```typescript
// Illustrative — not yet in the codebase. Shape confirmed against
// 02.1-UI-SPEC.md's Settings Screen & Toggle Contract → Persistence.
const STORAGE_KEY = 'keyboard-quest-settings' // exact key name is the planner's/executor's choice — not specified in CONTEXT.md or UI-SPEC
interface SettingsV1 {
  version: 1
  resetTrailOnMistake: boolean
}

function readSettings(): SettingsV1 {
  try {
    const raw = localStorage.getItem(STORAGE_KEY)
    if (!raw) return { version: 1, resetTrailOnMistake: false }
    const parsed = JSON.parse(raw)
    if (parsed?.version === 1 && typeof parsed.resetTrailOnMistake === 'boolean') return parsed
    return { version: 1, resetTrailOnMistake: false }
  } catch {
    return { version: 1, resetTrailOnMistake: false } // silent in-memory fallback
  }
}

function writeSettings(settings: SettingsV1): void {
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(settings))
  } catch {
    // Silent — matches celebrate.ts's "decorative/utility failures fail silently" precedent
  }
}
```
