  <action>
Add one pure function and change one expression. Everything else in this file stays byte-identical.

Add a module-private `function viewportScaleFactor(): number` co-located in `src/celebrate.ts`
(not a new module — this value has exactly one consumer and belongs next to it). Its body:
compute `widthRatio` as `window.innerWidth / 1280`, `heightRatio` as `window.innerHeight / 800`,
`factor` as `Math.sqrt(widthRatio * heightRatio)` — the geometric mean of the two ratios against
the 1280x800 baseline, so a window that grows in only one dimension scales more gently than one
that grows in both — and return `Math.min(2.5, Math.max(0.8, factor))`. The clamp is the safety
bound in both directions: a 640x480 window resolves to 0.8 rather than shrinking the already-tuned
Phase 1 burst below 80%, and an arbitrarily huge display resolves to 2.5 rather than launching
particles at unbounded velocity. A zero-width viewport during a fullscreen transition yields a
factor of 0, which the lower clamp lifts to 0.8.

The function is deliberately uncached, with no `resize` listener and no module-level memo: it is
called at fire time, so a fullscreen transition is picked up on the very next burst with zero
lifecycle state to clean up, and two cheap window property reads per burst are free next to the
canvas work that follows.

In `fireBurst()`, change only the `confetti({ ... })` argument: keep the existing `...opts`
spread and the existing `colors: CONFETTI_COLORS`, and add an explicit
`startVelocity: opts.startVelocity * viewportScaleFactor()` property after the spread so it
overrides the spread's own value. Place it so the scaled value wins over the spread — property
order matters here. The reduced-motion early return at the top of `fireBurst()` stays exactly
where it is, so under reduce-motion the scaling code is never reached and no confetti fires,
unchanged from Phase 1.

Scale NOTHING else. `particleCount`, `spread`, `ticks`, `gravity`, and `scalar` keep each
caller's existing distinct literal values — 40 / 60 / 150 / 1 / 0.8 in `celebrate()` and
120 / 100 / 200 / 1 / 1.1 in `celebrateAlphabetComplete()`. Leaving `ticks` and `gravity`
untouched is precisely what satisfies CELEB-02: the burst still resolves over the same number of
animation frames under the same deceleration curve, so a faster launch reads as a wider, further
throw rather than a sped-up one.

Do not edit `celebrate()` or `celebrateAlphabetComplete()` at all. They still pass base
`startVelocity` values of 25 and 35 respectively; the scaling concern lives solely in
`fireBurst()`, exactly like the reduced-motion guard already does. Note that
`celebrateAlphabetComplete()`'s three staggered bursts at 0/120/240ms each recompute the factor
independently — that is the accepted contract, not a defect, and must not be "fixed" with a
cached value.

Update the module head comment (currently describing `fireBurst()` as the module's single
reduced-motion guard site and single dynamic-import site) to record that it is now also the
module's single viewport-scaling site, so a future caller inherits all three concerns without
having to remember any of them.

This is one task rather than two because `noUnusedLocals` is enabled in `tsconfig.json`: a commit
that defines `viewportScaleFactor()` without calling it would fail `tsc` and leave the tree red.
  </action>
