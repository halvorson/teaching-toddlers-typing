<objective>
Give the trail its one user-facing control: a real, reachable, windowed Settings screen with a
single persisted "Reset trail on mistake" toggle (default off), and wire that persisted value
into gameplay so that when it is on, an incorrect key press wipes the whole trail.

Purpose: TRAIL-02. This is also the first phase to build any windowed panel content, the app's
first toggle control, and the app's first use of `localStorage` — Phase 3's sound toggle and
Phase 4's stats both extend exactly these three patterns, so they are established deliberately
here rather than improvised.
Output: `src/settings-store.ts` and `src/settings.ts` (both new), the panel/toggle CSS, the

</objective>

## Planning Decision — Settings uses menu chrome

The pattern map flagged an open question: should the Settings screen set `data-chrome="menu"` or
`data-chrome="game"`? **Resolved here as `"menu"`.** `02.1-UI-SPEC.md`'s panel contract requires
the Settings panel to render "over the same three-layer parallax background Phase 2 already
established", and `main.ts`'s current binary ternary would classify any non-menu screen as
`"game"`, which suppresses that background. Settings is also reached from and returns to the menu
and never enters fullscreen, so menu chrome is the consistent classification. The consequence is
deliberate and desirable: the star trail's `body[data-chrome="game"] #star-trail` visibility rule
keeps the trail hidden on Settings, which is correct — Settings is not gameplay. Task 2 widens
the ternary to `screen === 'menu' || screen === 'settings' ? 'menu' : 'game'`. Executors must not
substitute the existing binary form.

## Planning Decision — one shared settings record

The localStorage key is `keyboard-quest-settings` and holds a single record for the whole app,
`{ version: 1, resetTrailOnMistake: boolean }` — not a per-feature key. `02.1-RESEARCH.md`'s Open
Question 1 asked for this choice to be made explicitly rather than left implicit: Phase 3's sound
toggle and Phase 4's stats-reset preference should add fields to this same record and this same
interface, so the key name is deliberately feature-neutral.

**`src/settings-store.ts` (new).** Module-private `const STORAGE_KEY = 'keyboard-quest-settings'`.
Export `interface AppSettings { version: 1; resetTrailOnMistake: boolean }` and keep a
module-private `const DEFAULT_SETTINGS: AppSettings = { version: 1, resetTrailOnMistake: false }`.

- `export function readSettings(): AppSettings` — wrap the whole body in try/catch. Read
  `localStorage.getItem(STORAGE_KEY)`; if it is falsy return `DEFAULT_SETTINGS`. `JSON.parse` it,
  then shape-check the result before trusting it: the parsed value's `version` must be strictly
  `1` and `typeof parsed.resetTrailOnMistake` must be `'boolean'`. Anything that fails either
  check returns `DEFAULT_SETTINGS`. The catch also returns `DEFAULT_SETTINGS`. This shape check is
  the plan's ASVS V5 input-validation control (T-02.1-07): a value hand-edited in DevTools must
  degrade to the default, never throw and never coerce into unexpected behaviour.
- `export function writeSettings(settings: AppSettings): void` — `localStorage.setItem(STORAGE_KEY,
  JSON.stringify(settings))` inside a try/catch whose catch body is empty apart from a comment.
  Safari private browsing and quota exhaustion both make `setItem` throw; the documented contract
  is a silent in-memory-only value for the session with no error UI, matching this codebase's
  established "decorative and utility failures fail silently" precedent in `celebrate.ts` and
  `clipboard.ts`.
