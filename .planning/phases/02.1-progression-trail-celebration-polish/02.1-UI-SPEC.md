# Phase 2.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

Phase 2.1 is a narrow, two-part polish insertion on top of Phase 2's shipped menu/gameplay
shell: (1) a decorative ambient star trail that accumulates on every correct match during
gameplay, with a one-row Settings screen controlling whether it resets on mistakes, and (2)
a viewport-proportional scaling pass on the existing canvas-confetti celebration so bursts
read clearly on large/high-resolution displays. Per `02.1-CONTEXT.md`, this phase does **not**
touch Statistics (still Phase 2's stub, untouched) and does **not** add the sound toggle
(Phase 3's territory) — Settings gains exactly one row this phase.

This is the first phase to actually build a windowed panel's real content (Phase 2's
`02-UI-SPEC.md` only speculated about the Settings/Statistics panel pattern; this phase
implements it for Settings) and the first phase to introduce a toggle/switch control — there
is no prior visual precedent for either in the codebase, so both are specified in full below.

## Assumptions (gaps CONTEXT.md left open)

`02.1-CONTEXT.md`'s decisions are treated as authoritative. The items below fill gaps it
explicitly delegated to "Claude's Discretion" or left unstated — flagging them here so
planner/executor/checker can challenge any of them.

1. **shadcn/design-system tooling = none**, unchanged from Phases 1-2. Vanilla TypeScript,
   no framework (CLAUDE.md's "What NOT to Use" table); shadcn requires React. Gate resolves
   to "not applicable."
2. **Font = system UI stack**, unchanged from Phases 1-2.
3. **Star color/opacity is deliberately muted**, not full-saturation accent: core
   `color-mix(in srgb, var(--color-accent) 70%, transparent)`, glow
   `color-mix(in srgb, var(--color-accent) 45%, transparent)`. CONTEXT.md says "using the
   existing accent palette" but doesn't lock opacity; full-strength accent on a
   potentially-hundreds-of-dots ambient layer would contradict Phase 2's explicit design
   principle that accent must "still read as reserved, not ambient" (see `02-UI-SPEC.md`
   Color section — the 6% blob-layer opacity precedent this reuses the same reasoning from).
4. **Star placement needs no center-exclusion zone.** CONTEXT.md requires the trail "never
   obscures gameplay or legibility" — satisfied structurally by the z-index layering (trail
   renders below the target letter/UI, see Star Trail Contract), so a star landing "behind"
   the letter is simply occluded by it, never on top. Simple uniform-random placement within
   a small edge margin is sufficient; no rejection-sampling/avoidance logic needed.
5. **Toggle control is a custom `role="switch"` button**, not a native `<input type="checkbox">`
   — gives full visual control (track + thumb) with standard ARIA switch semantics and native
   click/Enter/Space activation, no extra JS needed for keyboard support. This is the app's
   first toggle; Phase 3's sound toggle should reuse this exact visual/markup pattern rather
   than inventing a second one.
6. **Settings persistence uses a small versioned localStorage schema**,
   `{ version: 1, resetTrailOnMistake: boolean }` — establishes the versioned-schema pattern
   STAT-02 (Phase 4) will later need for stats, applied now since this is the app's first
   persisted setting. Read/write wrapped in try/catch with a silent in-memory-only fallback if
   localStorage is unavailable (private browsing, quota, disabled) — no error UI, consistent
   with `celebrate.ts`'s existing "decorative/utility failures fail silently" precedent.
7. **The viewport-scale multiplier lives inside `fireBurst()` itself**, applied to whatever
   `startVelocity` it's given, rather than being computed separately in `celebrate()` and
   `celebrateAlphabetComplete()`. CONTEXT.md's code_context is explicit: "the viewport-scale
   multiplier should be threaded through this same helper, not duplicated per caller" — same
   pattern as the existing single reduced-motion guard site.
8. **Only `startVelocity` is scaled.** `particleCount`, `spread`, `ticks`, `gravity`, and
   `scalar` stay at each caller's existing distinct base values (40/60/150/1/0.8 ordinary;
   120/100/200/1/1.1 Alphabet-complete). CONTEXT.md scopes "travels further / covers more
   area" strictly to velocity while "keeping gravity/decay/ticks in the same ratio as today's
   tuning" — read as: those values are unchanged, not re-derived.
9. **Viewport-scale factor formula**: geometric mean of the width-ratio and height-ratio
   against the 1280×800 baseline, clamped to `[0.8, 2.5]`. CONTEXT.md names the baseline and
   the clamp range but delegates the exact formula — a concrete, deterministic choice is given
   below so the executor isn't guessing.
10. **Router gains a `'settings'` `Screen` member** (CONTEXT.md's own code_context flags this).
    Noted here for downstream awareness even though the router itself isn't a UI-SPEC-owned
    deliverable — it's what makes the Settings panel below reachable.
11. **Statistics screen is untouched by this phase** — stays exactly as Phase 2 left it (its
    stub copy, its windowed-panel treatment). Only Settings gets real content this phase.

## Star Trail Contract

*(Supplementary section — TRAIL-01/TRAIL-02 are fundamentally a rendering/lifecycle contract,
not static layout, so concrete values are specified here following Phase 1/2's precedent of
giving the executor exact numbers rather than leaving them to invent.)*

### Layer & stacking

- A dedicated `position: fixed; inset: 0;` layer (e.g. `#star-trail`), `pointer-events: none`,
  rendered above the existing drifting menu-background pseudo-elements and below all
  interactive/text UI (target letter, panel content), per CONTEXT.md's explicit ordering.
- Concretely: bump the existing `body::before`/`body::after` background layers (currently
  `z-index: -1` in `style.css`) down to `z-index: -2`, and give the new star-trail layer
  `z-index: -1`. `#app` and its children keep their existing implicit stacking (auto, above
  `-1`), so the trail sits strictly between the drifting background and all gameplay/menu
  content — no other z-index in the codebase needs to change.
- Visibility: **shown only during gameplay**, the exact opposite condition from the drifting
  background's existing `data-chrome="game"` suppression:
  ```css
  #star-trail { opacity: 0; transition: opacity 100ms ease-out; }
  body[data-chrome="game"] #star-trail { opacity: 1; }
  ```
  (Mirrors the existing `transition: opacity 100ms ease-out` already declared on
  `body::before`/`body::after` for consistency.)

### Star visual

- 6px diameter, `border-radius: 50%`, absolutely positioned within the layer:
  ```css
  .star-trail__star {
    position: absolute;
    width: 6px;
    height: 6px;
    border-radius: 50%;
    background: radial-gradient(circle,
      color-mix(in srgb, var(--color-accent) 70%, transparent) 0%,
      transparent 70%);
    box-shadow: 0 0 6px color-mix(in srgb, var(--color-accent) 45%, transparent);
  }
  ```
- Pop-in animation on creation:
  ```css
  .star-trail__star {
    opacity: 0;
    transform: scale(0.3);
    animation: star-pop-in 300ms ease-out forwards;
  }
  @keyframes star-pop-in {
    0%   { opacity: 0; transform: scale(0.3); }
    100% { opacity: 1; transform: scale(1); }
  }
  ```
- `prefers-reduced-motion: reduce`: stars appear instantly at full opacity/scale, no
  transition — per CONTEXT.md's explicit instruction, matching the existing reduced-motion
  pattern in `celebrate.ts` and the menu background:
  ```css
  @media (prefers-reduced-motion: reduce) {
    .star-trail__star {
      animation: none;
      opacity: 1;
      transform: scale(1);
    }
  }
  ```

### Placement

- Uniform random position per star, computed once at creation time, expressed in
  viewport-relative units so existing stars scale naturally on resize:
  ```
  left: `${2 + Math.random() * 96}vw`
  top:  `${2 + Math.random() * 96}vh`
  ```
  (2%–98% of each axis — small edge margin only, no center-exclusion zone; see assumption 4
  for why the z-index layering alone already satisfies "never obscures legibility.")
- No patterning/grid — pure `Math.random()` per star is sufficient (CONTEXT.md: "as long as it
  reads as scattered, not patterned").

### Lifecycle

- **Add**: one star appended on every correct match, alongside the existing `celebrate()` call
  site in `game-screen.ts`'s keydown handler.
- **Clear on mode entry**: the trail is cleared every time `mountGameScreen()` runs (initial
  launch and every subsequent mode switch alike) — each mode-entry starts empty, matching
  CONTEXT.md's "each mode starts with an empty trail." Not persisted across separate
  mode-entries, only accumulating within one continuous mount.
- **Clear on incorrect keypress — toggle-gated**: when the "Reset trail on mistake" setting is
  ON, an incorrect keypress triggers a **full** wipe (remove all star nodes, not a partial
  decay/fade) alongside the existing `incorrect-flash` trigger in the same handler branch. When
  OFF (default), incorrect keypresses have zero effect on the trail.
- **No cap/cycling logic** — CONTEXT.md is explicit this is not needed ("I don't think we need
  to program that"); effectively unbounded growth for a normal session is an accepted design
  choice, not a deferred gap.

  an in-memory-only value for the session — no error UI (assumption 6).

## Celebration Scaling Contract

*(Supplementary section — CELEB-01/CELEB-02 are a motion-tuning change to the existing
`celebrate.ts` module, not new layout. Concrete formula specified here so "scales relative to
viewport" isn't left ambiguous for the executor.)*

### Viewport-scale factor

Computed fresh on every burst (not cached, no resize listener needed — fullscreen transitions
are naturally picked up at fire-time):

```ts
function viewportScaleFactor(): number {
  const widthRatio = window.innerWidth / 1280
  const heightRatio = window.innerHeight / 800
  const factor = Math.sqrt(widthRatio * heightRatio) // geometric mean vs. 1280x800 baseline
  return Math.min(2.5, Math.max(0.8, factor))
}
```

### Where it's applied

- Lives **inside `fireBurst()`** (assumption 7) — multiplies whatever `startVelocity` its
  caller passed in, immediately before invoking `confetti(...)`:
  ```ts
  async function fireBurst(opts: BurstOptions): Promise<void> {
    if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) return
    try {
      const { default: confetti } = await import('canvas-confetti')
      confetti({
        ...opts,
        startVelocity: opts.startVelocity * viewportScaleFactor(),
        colors: CONFETTI_COLORS,
      })
    } catch {
      // unchanged — swallow load failures
    }
  }
  ```
- `celebrate()` and `celebrateAlphabetComplete()` are **unchanged** — they still pass their
  existing base `startVelocity` (25 and 35 respectively); the scaling concern lives solely in
  `fireBurst()`, exactly like the existing single reduced-motion guard.
- **Unscaled** (stay at each caller's existing distinct base value, per assumption 8):
  `particleCount` (40 / 120), `spread` (60 / 100), `ticks` (150 / 200), `gravity` (1 / 1),
  `scalar` (0.8 / 1.1). Only `startVelocity` moves.
- `celebrateAlphabetComplete()`'s three staggered bursts (0ms/120ms/240ms) each go through
  `fireBurst()` independently, so each recomputes `viewportScaleFactor()` at its own fire time
  — negligible drift risk given the ~240ms total window and no resize event realistically
  landing mid-sequence.

### Net effect on CELEB-01/CELEB-02

- **CELEB-01** (reads clearly on high-resolution displays): a 2560×1440 fullscreen viewport
  yields `factor ≈ sqrt(2 × 1.8) ≈ 1.9`, pushing ordinary `startVelocity` from 25→~47.5 and
  Alphabet-complete from 35→~66.5 — visibly larger travel radius without touching particle
  count/spread/size.
- **CELEB-02** (travels further, same speed): `ticks`/`gravity` are untouched, so the burst
  still resolves in the same number of animation frames — reads as "bigger," not "faster,"
  matching the ROADMAP's "at the same animation speed" requirement.
- Small windows (e.g. 640×480) clamp to `factor = 0.8`, never shrinking below 80% of today's
  already-shipped Phase 1/2 tuning.
