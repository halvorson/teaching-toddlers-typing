## Virtual-Keyboard Summon Behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Stay open all session | One tap opens it; hidden input silently re-focused after each match/blur so the keyboard never disappears mid-session. | ✓ |
| Re-tap required each time | Simpler to implement, but breaks hunt-and-peck flow between letters. | |

**User's choice:** Stay open all session.
**Notes:** Chosen specifically to protect the Core Value's instant, uninterrupted feedback loop on mobile.

| Option | Description | Selected |
|--------|-------------|----------|
| Open-only, no explicit close | Icon always (re)focuses the hidden input; dismissal left to OS/browser. | ✓ |
| Tap toggles open/closed | Second tap explicitly blurs the input to hide the keyboard. | |

**User's choice:** Open-only, no explicit close.

| Option | Description | Selected |
|--------|-------------|----------|
| Always require the first tap | Consistent, predictable across devices; avoids an unrequested keyboard covering the target letter on load. | ✓ |
| Auto-open on mobile screen mount | Zero-tap start on touch devices; requires reliable mobile detection. | |

**User's choice:** Always require the first tap.

| Option | Description | Selected |
|--------|-------------|----------|
| Static appearance always | Icon never tracks keyboard open/closed state. | ✓ |
| Highlight when open | Icon visibly changes while keyboard is open. | |

**User's choice:** Static appearance always.

## Physical-Key-Matching Fallback on Mobile

| Option | Description | Selected |
|--------|-------------|----------|
| Fall back to `.key` on mobile only | When `.code` is missing/"Unidentified" from the virtual-keyboard-summoned input, match `event.key` (case-insensitive) instead. Physical keyboards unaffected. | ✓ |
| Require `.code` everywhere, even on mobile | No fallback — some virtual-keyboard taps may not register at all. | |

**User's choice:** Fall back to `.key` on mobile only.
**Notes:** This directly addresses the technical uncertainty this phase was isolated from Phase 4.1 to de-risk.

| Option | Description | Selected |
|--------|-------------|----------|
| Applies to all three modes uniformly | Same fallback logic across Letters, Numbers, Alphabet. | ✓ |
| You decide | Leave scoping to Claude's judgement. | |

**User's choice:** Applies to all three modes uniformly.
**Notes:** User added a new request mid-answer: in Numbers mode, request a numeric/digit (10-key) virtual keyboard layout if the browser supports it (e.g. `inputmode="numeric"` or `type="tel"`), best-effort with graceful degradation. Captured as D-07 in CONTEXT.md.

## Icon Visibility Condition

| Option | Description | Selected |
|--------|-------------|----------|
| Always render | No device-detection branch; subtly-shaded so it's harmless on desktop. | ✓ |
| Touch/coarse-pointer only | Hidden on mouse/trackpad devices via feature detection; risks misfiring on hybrid devices. | |

**User's choice:** Always render.
**Notes:** User refined this with a direct request: implement an `isVisible`-style stub function that currently always returns `true`, so a real device-detection condition can be dropped in later without restructuring the call site.
