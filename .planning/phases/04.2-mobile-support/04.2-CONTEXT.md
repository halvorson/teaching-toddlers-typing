# Phase 4.2: Mobile Support - Context

**Gathered:** 2026-08-15
**Status:** Ready for planning

<domain>
## Phase Boundary

A player without a physical keyboard can still play. Two additions to the existing
Letters/Numbers/Alphabet gameplay screens: (1) a subtly-shaded corner icon that summons the
device's on-screen/virtual keyboard, wired so its taps drive the same physical-key-matching
gameplay loop, and (2) a visible on-screen back control that returns to the home menu,
alongside the existing Escape support (MOBILE-01, MOBILE-02). This phase was isolated from
4.1 specifically because touch/virtual-keyboard event handling has no prior precedent in this
codebase — higher technical uncertainty than 4.1's settings/UI work.

</domain>

<decisions>
## Implementation Decisions

### Virtual-Keyboard Summon Behavior (MOBILE-01)
- **D-01:** Tapping the keyboard-summon icon focuses a hidden `<input>`, and that focus is
  **silently re-applied after every match** (correct or incorrect) so the on-screen keyboard
  stays available for the rest of the session after a single initial tap — the child should
  never need to hunt for the icon again mid-session. This directly protects the Core Value's
  instant, uninterrupted feedback loop on mobile. **Reversibility:** reversible — a
  refocus-after-match call is easy to remove if it causes problems (e.g. unwanted repeated
  keyboard-open animations).
- **D-02:** The icon is **open-only, no explicit close/toggle** — every tap (re)focuses the
  hidden input; there is no second-tap-to-dismiss behavior. Dismissing the OS/browser virtual
  keyboard (tap elsewhere, back gesture, etc.) is left entirely to the platform, same as any
  ordinary mobile text field.
- **D-03:** The virtual keyboard **never auto-opens** on mobile/touch screen mount — the first
  tap on the icon is always required, on every device. Avoids an unrequested keyboard covering
  the target letter before the child has even seen it, and keeps behavior consistent between
  desktop and mobile.
- **D-04:** The icon has **no visible open/closed state change** — it stays visually static
  (subtly-shaded, per MOBILE-01's own wording) regardless of whether the hidden input currently
  has focus. No focus/blur state needs to be tracked for display purposes.

### Physical-Key-Matching Fallback on Mobile
- **D-05:** PROJECT.md's existing lock — matching via `KeyboardEvent.code` (physical key
  position), never `.key`/character — is **preserved everywhere it already works**. A
  mobile-only fallback is added: when a keydown event's `.code` doesn't identify a key (empty
  string or `"Unidentified"`) **and** the event originated from the virtual-keyboard-summoned
  hidden input, match against `event.key` instead (case-insensitive). Physical keyboards
  (desktop, or a mobile device with one attached) are unaffected and keep using `.code` exactly
  as today. **Reversibility:** reversible but load-bearing — this is the one mechanism that
  makes mobile gameplay actually work; removing it would likely make virtual-keyboard taps
  silently fail to register on browsers where `.code` isn't populated reliably (this was the
  specific technical risk this phase was split out to isolate).
- **D-06:** The `.key` fallback applies **uniformly to all three modes** (Letters, Numbers,
  Alphabet) — no mode-specific exclusions, mirroring how `acceptableCodes()` in `game.ts`
  already branches only on digit-vs-letter, not per-mode special cases.
- **D-07 (user-added mid-discussion):** In **Numbers mode**, the hidden input should request a
  numeric/digit (10-key) virtual keyboard layout where the browser supports it — e.g. via
  `inputmode="numeric"` or `type="tel"` — instead of the default full alphabetic layout. This
  is **best-effort**: if a browser doesn't honor the hint, gameplay still works via whatever
  keyboard the browser shows and the D-05/D-06 matching fallback. This is a keyboard-*layout*
  request only; it does not change the `.code`/`.key` matching decision above. Feasibility
  details (which attribute combination is most reliable cross-browser) are research/planner
  territory.

### Back Control Style & Placement (MOBILE-02)
- **D-08:** The on-screen back control is a **small corner icon** — the same subtly-shaded
  visual treatment and weight as the keyboard-summon icon (e.g. a back-arrow/chevron) — not a
  reuse of Settings' windowed `.panel-back` "← Back" text button. Gameplay screens are
  full-immersive (just the target letter, no panel chrome), so the text-button pattern doesn't
  fit visually; the new icon should look like a sibling of the keyboard icon, not an import
  from the Settings screen.
- **D-09:** The back icon sits in the **opposite corner from the keyboard icon** — top-left,
  mirroring MOBILE-01's top-right keyboard icon symmetrically. Two distinct corners reduce the
  chance of a toddler tapping the wrong control by accident.
- Activating the back icon calls the same `onQuit`/`quitToMenu` callback already passed into
  `mountGameScreen` and wired to the existing Escape handler (per Phase 4.1's D-01, which
  explicitly flagged this hookup for Phase 4.2) — no new navigation path, just a second trigger
  for the existing one.

### Icon Visibility Condition
- **D-10:** Both the keyboard-summon icon and the back-control icon **always render** on
  gameplay screens, on every device — no touch/coarse-pointer feature detection gating
  visibility. They're harmless (and simply unused) on desktop since they're subtly-shaded per
  MOBILE-01's wording; this avoids getting device-detection edge cases (hybrid/touchscreen
  laptops, etc.) wrong.
- **D-11 (user refinement):** Implement visibility through an **`isVisible`-style stub
  function that currently always returns `true`**, rather than inlining "always show" directly
  at each call site. This makes it trivial to drop in a real device-detection condition later
  without restructuring the icon-mounting code. Exact function name/location is Claude's
  discretion; the point is the seam exists, not the specific value it currently returns.

### Claude's Discretion
- Exact TypeScript function/module names (the `isVisible` stub, the hidden-input mounting
  function, the mobile-fallback matching helper).
- Whether the hidden input lives in `game-screen.ts` directly or a new small module — follow
  whatever the researcher/planner finds keeps `game-screen.ts`'s existing shape (idempotent
  mount/unmount, single keydown listener) cleanest.
- Exact SVG glyph paths for the keyboard-summon and back icons (follow `menu.ts`'s existing
  inline-`<svg>` share-icon pattern for construction style, not literal shape).
- Precise `inputmode`/`type` attribute value(s) used for D-07's numeric-keyboard request —
  cross-browser reliability is a research question, not a locked decision.
- Whether "originated from the virtual-keyboard-summoned hidden input" (D-05's fallback gate)
  is detected via event target identity, a module-level flag, or another mechanism — the
  *behavior* (fallback only applies to virtual-keyboard-originated events, never silently
  widens physical-keyboard matching) is locked; the mechanism is not.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/game-screen.ts` — `mountGameScreen(container, mode, onQuit)`'s single document-level
  keydown listener and idempotent mount/unmount shape is where the mobile `.code`→`.key`
  fallback (D-05) and the hidden input's focus-after-match refresh (D-01) both need to hook in,
  alongside the existing correct/incorrect branches. `onQuit` (already threaded through to the
  existing Escape handler) is the exact callback the new back icon (D-08/D-09) should call —
  no new navigation wiring needed, confirmed directly relevant per Phase 4.1's 04.1-CONTEXT.md
  D-01 note that this hookup was deliberately deferred to this phase.
- `src/menu.ts` — the inline `<svg>` icon-construction pattern (`SVG_NS =
  'http://www.w3.org/2000/svg'`, `document.createElementNS`, `viewBox`/`aria-hidden="true"`/
  `focusable="false"` attributes, used for the existing Share row icon) is the established
  precedent to follow for building both new icons — keeps icon construction consistent
  codebase-wide rather than introducing a new icon-authoring approach (e.g. an icon font or
  external SVG file).
- `src/settings.ts` — `mountSettingsScreen`'s `.panel-back` "← Back" button exists as a back-
  control precedent, but per D-08 is explicitly **not** the visual pattern to copy for gameplay
  screens (windowed-panel look vs. full-immersive gameplay look) — still worth reading for how
  it wires a back button to a callback via delegated click listener, which is the same wiring
  shape the new gameplay back icon needs.
- `src/game.ts` — `acceptableCodes(target, mode)` is the single function that currently decides
  what counts as a correct physical-key match; the mobile `.key` fallback (D-05/D-06) is an
  addition alongside/around this function, not a replacement of its existing `.code`-based
  logic for physical keyboards.

### Established Patterns
- Fire-and-forget, silent-degrade-on-failure for anything platform/browser-dependent —
  `fullscreen.ts`'s `enterFullscreen`/`exitFullscreenIfActive` (catches and swallows rejected
  promises, no error UI) is the direct precedent for how the virtual-keyboard-summon focus call
  and the `inputmode`/`type` numeric-keyboard hint (D-07) should degrade when unsupported: no
  error surfaced to the child, gameplay keeps working via existing paths.
- `textContent`-only / no-`innerHTML` DOM construction, codebase-wide invariant — applies to
  both new icons and the hidden input's setup.
- Document-level (not container-level) keydown listener registration, single listener per
  mount, added in `mountGameScreen` and removed in `unmountGameScreen` — the mobile-fallback
  matching logic and the keyboard-summon input both need to respect this existing lifecycle
  rather than introducing a second/parallel listener.

### Integration Points
- `game-screen.ts`'s `mountGameScreen`/`unmountGameScreen` — gains the hidden input's
  creation/cleanup, the keyboard-summon icon, the back icon, and the mobile-fallback branch in
  the existing keydown handler.
- `game.ts`'s `acceptableCodes` — either gains a sibling function for the `.key`-based fallback
  check, or `game-screen.ts`'s handler calls both and combines results; exact shape is Claude's
  discretion (see above).
- No changes anticipated to `menu.ts`, `settings.ts`, `settings-store.ts`, `celebrate.ts`,
  `trail.ts`, or `audio.ts` — this phase is scoped entirely to the three gameplay-mode screens.

</code_context>
